01

框架怎么组织

Deep Agents 提供总控委派、角色上下文和工具调用能力，底层基于 LangGraph。项目在外层用业务 DAG 固定步骤与用户选择点，实际写作和审核统一落到内容服务。

步骤由业务 DAG 决定

当前主阶段是 script → content_review → 等待用户选稿。Agent 不能自行越过选择点。

角色通过工具办事

默认采用确定性的调用序列。写作与审核模型由内容服务调用；这不等于让大模型自由规划全部流程。

恢复依靠业务记录

保存工作项、内容任务和供应商作业。重启后按状态续跑，已完成的请求复用结果。

两个容易混淆的点：点击内容页面按钮不一定经过 Deep Agents；Agent 工具复用的生成任务本身已经包含“写作 → 审核 → 有限返工”。独立审核指不同模型、上下文和审核记录，不要求每次审稿都再开一个外层 Agent 工作项。

03

工具有很多，MCP 是接入协议

热点获取、主播形象、音频、数字人视频，都是具体的工具能力。一个 MCP 服务可以暴露多个工具；一个 Python 文件也能登记多个能力。不能用 MCP 服务数或文件数来代表工具数量。

Skill：怎么做

角色的工作说明书。约定输入、步骤、输出与拒收条件；它本身不执行 API 请求。

Tool：执行什么

执行一个具体动作，例如搜索热点、合成配音、提交数字人视频。每个动作有自己的输入与结果。

MCP：怎么接

向 Agent 公开工具的标准协议。工具也可以直接注册成原生函数；只有经 MCP 服务暴露的工具才是 MCP tools。

项目的工具能力全景

内容多 Agent 协作与媒体工具调用同时存在。音频、数字人不再设置导演 Agent，主控通过受控工具调用其业务服务。

总控可调用的工具

热点搜索、参考视觉分析、人设 / 资产查询、表达计划、音频合成、动作 / 嘴型、数字人 / 单段 Wan 视频、作业查询。

写作：提交三稿、提出经验候选。

Skill 为这些角色提供工作方法

S01 · 选题与新意

使用者：写作 Agent

明确受众和具体问题，规划三个有差异的角度；未知事实标记待核，不编造热度、数字和来源。

S02 · 内容写作

目录名仍为“口播写作”

口播路线交付自然可朗读的正文；分镜路线交付画面、台词、音效、时长与 Wan 提示词。借鉴叙事方式，避免照搬独特表达。

S03 · 事实与重复审核

使用者：审核 Agent

核对事实依据、原创性和三稿差异；分别检查口语表达或分镜可制作性。每个问题给出具体位置和可执行改法。

当前执行路径把已登记的 Skill 正文加入角色提示，并记录文件摘要；Skill 缺失会阻断。Skill 指令负责引导，权限白名单、审核绑定和费用校验由业务代码执行。两类专业 Agent 还可提交 propose_memory 经验候选，候选不等于已生效的长期知识。

一次工具调用，实际经过这些步骤

Agent 提出调用→角色白名单→归属与参数校验→幂等与业务门禁→共享业务服务→产物引用 + 审计

例如：主控调用 search_douyin，工具向内容任务层提交搜索，再由 RedFox 适配器访问供应商。写作 Agent 消费选定的参考快照。

一个 mcp.py，并不代表一个工具

这个文件已登记稿件、表演计划、质量报告、TTS、动作、嘴型、数字人视频和云视频等多个能力，并提供提交 / 查询接口。它也不是整个项目唯一的工具注册表；实际角色工具见 agents/tools.py 与 roles.py。

当前如何连接这些能力

目前通过原生 Agent 工具、业务 API、Provider 适配器及 Worker 执行；未发现标准 MCP Server / Client 的生产连接。以后若采用 MCP，可以按内容、形象、音频、视频分组，也可以由一个服务公开多个工具，分组数不等于能力数。

实现细节：框架默认工具与 Skill 版本

Deep Agents 使用内存 StateBackend。通用写文件与 shell 能力被移除；框架强制保留的 read_file 只面对未注入业务文件的内存空间。生产执行显式加载可信 Skill 内容。

当前登记代码的 Skill 版本常量为 0.2.0，S02 / S03 正文声明为 0.3.0；文件摘要仍会变化。这份文档不把该差异描述为已统一的版本管理。

04

用户业务流程

两条路线共享检索、写作和审核；交付格式及选稿后的制作流程不同。以下展示参考驱动的创作流程，页面仍可使用已有主题与资料直接写作。

  1. 1

    定义创作任务

    用户选择路线，填写主题、受众、目标时长和账号风格；事实资料单独提供。

  2. 2

    搜索并选择参考

    RedFox + 用户搜索相关作品，显示可取得的互动数据、封面和原视频链接；用户选择主参考后才深入提取。

  3. 3

    导入参考，形成快照

    内容任务分别保存标题、简介和音频转写，记录远端转写 taskId。分镜参考没有有效口播时，可经用户确认使用视频画面分析；标题、简介不能冒充转写。

  4. 4

    整理写作提示

    Qwen + 用户分析参考的结构、开头与节奏，结合账号风格生成可编辑提示，并规划三种角度。

  5. 5

    生成三份候选

    Claude按当前路线的结构交付三个不同角度的原创稿，连同事实断言和来源依据进入审核。

  6. 6

    先审核，再展示

    业务规则 + Qwen规则检查事实和结构，独立模型审核表达、原创性及三稿差异。不通过的候选按具体意见返工，默认最多自动返工 2 轮。

  7. 7

    用户选定一份

    用户 + 后端校验三份候选及整组审核全部通过，页面才显示正文。选稿接口再次校验版本和审核，随后记录用户采用决定。

展示条件 = 三稿齐全 + 三份单稿通过 + 整组通过 + 版本仍一致

不足三份合格稿时，保留问题与返工入口，候选正文继续隐藏。已通过的稿保留；修改失败稿后，重审修改项及整组差异。

交互示意：
不展示正文，继续返工未通过项。

此处仅演示规则，不执行生成或付费调用。

口播稿交付

标题、角度、正文、预计时长、事实断言与审核记录。

用户选稿 → 配置音色与表达 → 确认费用 → 音频生成 → 用户选择的数字人路线 → 合成 / 发布 Worker。OmniHuman 仍按实际音频时长执行限制，不能靠文稿估时放行。

分镜剧本交付

逐镜头：画面、台词 / 旁白、音效、时长、Wan 提示词。当前分镜契约要求每镜头 2–30 秒整数时长。

用户选稿 → 构造逐镜头任务图 → 确认生图预算 → 逐镜头生图 → 用户确认图片与 Wan 费用 → Wan 逐镜头生成画面和声音 → 确认原片 → Worker 顺序拼接，做短音频过渡 → 确认成片。

多镜头累计时长可超过 60 秒。这条路线不依赖外部配音；独立生成镜头不保证动作与音色连续，应在剧本中设计明确的场景切换。

内容与制作的交接点就是用户选稿。Deep Agents 的自动内容工作图在这里等待。音频、数字人可由主控受控工具调用，付费提交仍需匹配的用户确认；最终拼接、合成和自动发布由 Worker 执行。

05

数据怎样流转

输入决定提示，提示生成稿件，审核绑定这些输入与稿件版本，用户选择绑定审核后的产物。作品保存“当前采用哪一版”，历史记录继续留存。

01 · 创作要求

主题与风格

Work.brief · StyleProfile

主题、受众、路线、时长、账号风格。作品使用风格快照，避免模板改动悄悄改变旧任务。

02 · 参考输入

不可变参考快照

ReferenceSnapshot

原链接、标题、简介、转写、互动数据与分析结果。更新内容时保存新快照，并保留父版本。

03 · 写作指令

提示与角度计划

PromptDocument

绑定参考、要求与风格摘要。用户编辑提示产生新版本；它决定这一批稿件的写法。

04 · 内容产物

稿件版本与三稿批次

ScriptVersion · BatchRecord

每一稿拥有版本 ID；批次记录 slot 1 / 2 / 3 对应的稿件。返工生成新版本，不覆盖原稿。

05 · 质量依据

单稿与整组审核

QualityDecision

单稿审核针对具体正文 / 分镜；整组审核针对三个候选的组合。审核结果必须匹配当前输入。

06 · 用户决定

采用记录与下游输入

SelectionDecision

记录用户选定的稿件和审核。媒体链读取已采用版本；自动评分不能替用户选稿。

主数据流：创作要求 + 参考 → 写作提示 → 三稿版本 → 审核决定 → 用户采用
独立事实输入：用户资料 / 可核验证据 → 写作与审核。参考视频默认是灵感，热门内容中的说法不会自动变成已核实事实。

为什么改一句话也要重新检查

比如用户把稿件中的“可能改善”改成“一定有效”，旧审核不能继续有效。系统通过摘要绑定输入；改稿后，单稿审核和三稿组合审核需更新，旧的采用及下游当前绑定也可能撤销，历史文件仍保留。

正文 / 完整分镜参考快照事实证据创作要求风格写作提示候选集合
06

任务怎么运行，出错后怎么恢复

AgentWorkItem

记录哪个角色在做哪一步，依赖什么输入和 Skill。产出 AgentResult，必须包含可追溯的产物引用。

content_jobs

一次业务操作：搜索、导入、整理提示、生成、返工或审核。页面用 job_id 查询进度。

provider_jobs

一次供应商请求：模型调用或 RedFox 任务。记录预算、请求摘要、状态、结果和远端 taskId。

  • 提交和查询分开：写操作返回 202 + job_id；GET 只读。需要更新远端转写结果时，显式刷新原作业。
  • 每次外部调用先记账：预算预留 → 保存发送状态 → 发送一次 → 保存响应与结算。相同幂等键返回原结果。
  • 两个等待点分清：三稿合格是质量条件；waiting_selection 是等待用户选择。通过审核不会自动进入付费制作。
07

视觉理解并入哪里

让系统读懂“没有口播的画面”

源码已有接入 · 真实效果未验收

RedFox 转写解决“说了什么”；视觉模型补充“画面里发生什么”。跳舞、带 BGM 的视频即使转写为空，仍可能有可用于分镜创作的动作、场景和镜头信息。

本次重新核查到的入口

页面画面分析、费用确认 API、visual_analysis 内容任务、总控工具及 Qwen-VL 适配器均已出现。分镜参考已允许有效转写或有效视觉结果。

工具如何进入 Agent 工作流

分镜参考缺少有效转写与视觉结果时，总控增加视觉准备工作项。缺视频或有效费用确认时返回用户操作要求；写作 Agent 只消费准备好的参考。

真实视频文件 / 直链→visual_analysis 任务→抽帧 + Qwen-VL→新参考快照→写作与审核

主控工具是 analyze_reference_visual：它与页面复用内容任务、费用确认和幂等机制，写作与审核不各自重复请求视觉模型。

以上为源码接入关系，本次未执行真实视频分析验收。口播参考仍要求有效转写；视觉观察不自动成为事实证据，抖音网页地址本身也不能当作视频文件。
