# 自媒体视频生成系统部署方案

版本：2026-10-08。用于答辩与部署规划；建议配置和成本均为规划值，未代表已完成生产部署或容量验收。

## 一、生产环境（答辩重点）

架构：应用控制面、媒体后期、GPU 推理与浏览器发布分离。当前先沿用 Windows 单实例工作台 + Linux GPU 节点；下列多节点布局属于完成改造后的生产目标。

```text
【服务器1：Web 入口 + API + 内容创作】
  - 建议配置：8 核 CPU + 16 GB 内存 + 200 GB SSD，Linux
  - Nginx：托管 Vue 3 / TypeScript / Pinia / Vite 构建后的 dist
  - HTTPS 443；反向代理 FastAPI / Uvicorn，API 仅私网可达
  - FastAPI 初期 1 个 worker，不直接启动 4 个 worker
  - DeepAgents：进程内策划、写稿、审核与工具编排
  - 业务 Skill：按阶段加载规则；人工审核通过或手工修改确认后采用
  - 降级：DeepAgents 异常时独立内容流程；模型不可用时人工编辑 / 导入
  - 扩容前：拆唯一内容调度器，补任务 owner、租约和心跳恢复

【服务器2：视频拼接 + 字幕烧录】
  - 建议配置：16 核 CPU + 32 GB 内存 + 500 GB SSD，Linux
  - 分镜拼接 Worker：python -m app.short_video.worker --loop
  - 字幕 Worker：python -m app.short_video.subtitle_jobs --loop
  - FFmpeg / ffprobe / libass：拼接、音轨提取、ASS 烧录、SRT 导出
  - 当前编码为 libx264，主要消耗 CPU，不假定已经使用 GPU 编码
  - 字幕时间轴来自成功的 ASR / 强制对齐，不用估算时间轴兜底
  - 初期每类 Worker 1 个；按实测编码时间、队列长度再扩容
  - 拆机前：统一媒体路径和共享挂载，适配路径与授权中文字体

【服务器3：GPU 模型推理】
  - 建议配置：8–16 核 CPU + 32–64 GB 内存 + 500 GB SSD
  - 1 张支持 BF16 的 NVIDIA GPU，建议显存 24–32 GB
  - LivePortrait：动作迁移；MuseTalk：人物口型生成
  - Qwen3-ASR-1.7B：语音识别；Qwen3-ForcedAligner-0.6B：字幕对齐
  - 三套独立 Python 推理环境，共用单 GPU 串行队列
  - HTTP Worker 通过私网或 SSH 隧道访问，携带鉴权令牌
  - 按需开机；模型 API 写稿、图片、Wan 视频无需占用本节点
  - 生产必补：GPU 作业索引持久化、恢复与幂等结果核对
  - 显存为选型建议，最长视频和真实模型验收后再确定采购规格

【服务器4：抖音浏览器发布】
  - 建议配置：4 核 CPU + 8 GB 内存 + 100 GB SSD，Windows 交互桌面
  - Playwright + 可见 Chrome；专用登录 profile 持久化
  - 同一账号同一时刻只运行一个发布会话
  - 用户完成扫码 / 验证、投稿内容核对与最终发布确认
  - 初期可复用现有电脑；服务器报价需另核 Windows 授权
  - 当前发布线程在 API 进程内；独立部署需新增远程发布 Agent
  - 上传准备成功、提交回执与平台审核通过是不同状态

【数据库：PostgreSQL】
  - 建议配置：4 核 CPU + 8 GB 内存 + 100 GB SSD，托管数据库优先
  - 保存作品、分镜、人工审核、任务、版本、预算和外部调用账本
  - 已接入 psycopg 3；当前写事务使用 PostgreSQL advisory lock
  - 仅私网访问；每日备份，按业务要求开启 WAL 归档与恢复演练
  - 当前无需 Milvus / Elasticsearch；Redis 也不是现有必需依赖
  - 后续按需增加 Redis 队列 / 缓存，须同时实现租约与任务恢复

【存储 + 监控】
  - 媒体：当前 runtime 本地文件 + 火山 TOS 供应商素材传递
  - 初期跨节点使用相同路径的共享挂载；归档目标为 TOS 对象存储
  - 当前 TOS 素材传递不等于所有成片已迁到对象存储
  - 私有桶 / 有效期 URL / 生命周期需做供应商兼容与代码改造
  - 建议增加 Prometheus + Grafana + Loki，初期与应用节点合部署
  - 监测队列等待、unknown 任务、GPU 显存、磁盘、供应商余额和失败率

【外部模型与数据 API：无需自建 GPT 推理服务器】
  - 写稿 / 定向返工：gpt-6.1-sol
  - 策划 / 独立审核：gpt-6-astra
  - 人物 / 分镜图片：GPT Image 2.5
  - TTS：MiniMax speech-2.8-hd
  - 分镜视频：百炼 wan3.0-video；云端口播：OmniHuman 1.5
  - 参考检索 / 转写：红狐 API；参考画面分析：Qwen3-VL
  - 密钥只放后端秘密配置；预算、限流与未知结果核对统一记账
```

推荐数据流：浏览器 → Web/API → 内容生成与模型检查 → 人工审核 / 修改采用 → 图片与视频 API / GPU 口播 → CPU 拼接 → GPU ASR 与对齐 → CPU 烧录字幕 → 交付包 → 浏览器发布确认。PostgreSQL 记录各阶段状态，媒体存储保存原件和成片。

## 二、成本估算

按小团队试运行规划：每月约 30 条成片，每条 30–60 秒，平均 6 个镜头；GPU 开机 120 小时 / 月，估算单价 3 元 / 小时。此负载仅用于预算，不构成产能保证。所有金额为预算示例，未查询实时云报价；外部 API 项是月度预留额度，不是已核实的模型单价，含返工余量。税费、Windows 授权和首次开发改造另计。

| 资源 | 配置 / 计费假设 | 月成本示例 | 说明 |
| --- | --- | ---: | --- |
| 应用服务器 | 8 核 / 16 GB | ¥450 | Web、API、内容调度 |
| 媒体服务器 | 16 核 / 32 GB | ¥750 | FFmpeg 拼接与字幕烧录 |
| PostgreSQL | 4 核 / 8 GB / 100 GB | ¥400 | 业务数据与任务账本 |
| 发布节点 | 4 核 / 8 GB | ¥300 | 可复用已有电脑，授权另核 |
| GPU | 1 张，120 小时 × ¥3 | ¥360 | 24–32 GB 档预算占位，采购需报价与压测 |
| 对象存储 / 备份 | 约 500 GB | ¥100 | 原件、成片、备份；不含服务器 SSD |
| 公网流量 | 约 300 GB / 月 | ¥100 | 含供应商素材下载，按计费口径复核 |
| 日志 / 监控留存 | 30 天 | ¥60 | 软件可开源，费用预留给留存资源 |

| 图片 API | 月预算 | ¥400 | 人物、分镜、重生成 |
| TTS API | 月预算 | ¥200 | 按字符或供应商账单 |
| 视频 API | 月预算 | ¥1,400 | Wan / OmniHuman；M2 替代部分口播可再估 |
| 红狐 / 参考视觉 API | 月预算 | ¥200 | 检索、转写、画面分析 |

若 GPU 按同一假设整月开机 720 小时：GPU 成本为 ¥2,160，总预算为 ¥7,320 / 月。已有电脑承载本机工作台与发布、PostgreSQL 同机时，可省四项服务器预算 ¥1,900 和监控留存预算 ¥60，示例预算约 ¥3,560 / 月；不含已有硬件购置、电费和维护成本。

成本公式：月成本 = CPU / 数据库资源 + GPU 小时 × 小时单价 + 存储 + 流量 + 监控留存 + 文本 / 图片 / 语音 / 视频 / 数据 API 实际调用费用。

## 三、当前可落地部署

```text
【主机A：现有 Windows 工作台】
  - 建议 8 核 CPU + 32 GB 内存 + 1 TB SSD
  - Vue 构建产物、FastAPI 1 worker、进程内 DeepAgents
  - PostgreSQL、分镜拼接 Worker、字幕 Worker、FFmpeg / libass
  - 可交互 Chrome 与发布适配器放在同一主机
  - 默认仅本机访问；团队内网访问前增加认证与访问控制

【主机B：Linux 算力云】
  - 四阶段 GPU Worker，单 GPU 串行
  - 私网 / SSH 隧道访问，按需开机

【云服务】
  - 外部模型 API + 火山 TOS
  - 数据库、媒体、浏览器 profile 与密钥分别备份
```

这条路线符合当前程序边界。现有 `production/start.ps1` 启动的是 Vite 开发服务；正式部署应构建 `dist` 并配置静态服务器，而不是把 5173 作为生产入口。当前 GPU 连接保持关闭，本方案不执行开机、连接或部署。

## 四、生产化实施顺序

1. 固定依赖与发布版本，备份 PostgreSQL、媒体、角色配置和浏览器 profile；在独立目录恢复验证。
2. 构建前端 `dist`，配置 HTTPS 反向代理、认证、权限、上传限额与 CORS；先以 1 个 API worker 上线内网。
3. 拆内容调度器，完善 owner / 租约 / 心跳恢复；保持未知付费请求先核对再决定是否重生成。
4. 统一媒体 URI 与共享路径，独立部署 CPU 后期节点；Linux 验证中文字体、libass、字幕时间轴与成片音轨。
5. 持久化 GPU 作业与幂等索引，验证断线、进程重启和中途失败不会重复提交。
6. 新增远程发布 Agent，隔离账号 profile、转移媒体并保留人工确认；完成真实发布授权验收。
7. 增加监控、磁盘与余额告警；完成端到端、并发和恢复验收后再扩 API 与 Worker 副本。

验收至少覆盖：修改剧本与人工采用、生成任务幂等、未知请求核对、合成视频音画检查、字幕烧录与 SRT 导出、数据库与媒体恢复、浏览器上传准备。最终发布需要另行明确授权；健康检查不替代真实制作和发布验收。

## 五、答辩表述

“系统采用混合部署：应用层承担内容编排和人工审核，CPU 节点负责视频拼接与字幕烧录，独立 GPU 节点完成数字人口型和语音对齐，浏览器节点处理抖音投稿。业务状态已存入 PostgreSQL，GPT、图片、TTS 和分镜视频通过外部 API 调用。当前可落地的是单实例工作台加云端 GPU；多节点方案需要补齐调度恢复、共享媒体和远程发布，成本按按需 GPU 与模型调用预算分别计算。”
