对应原汇报第 1 块 · 结论与边界

我们到底在做一个什么项目？

这是一个数字人口播视频制作工作台，把从选题到交付的工作组织起来。

你提供主题，选择人物和声音；系统协助写稿、生成配音、制作数字人视频、添加字幕和封面，最后产出可下载、可用于发布的成品包。项目采用的是“AI 生成 + 程序检查 + 关键步骤人工确认”的工作方式。

你自己使用，打开页面，选择素材，生成和审核作品。遇到问题可以人工处理。重点是把制作能力和操作流程接起来。

02

对应原汇报第 2 块 · 总体架构

系统里的每一层，都负责什么？

架构图回答的是：为了完成一条视频，谁接收操作、谁安排工作、谁执行、谁保存结果。

工作台接收你的操作 → Agent 协调工作 → 业务程序检查条件 → 模型和 Worker 执行任务 → 数据库与文件保存结果。

第一层：工作台 / API——你操作系统的入口

工作台就是你看见的网页：选人物、看三篇稿件、试听、生成视频、查看进度、下载。API 可以理解成网页与后台之间的办事窗口。

例如点击“生成配音”，网页会向后台提出请求：“请给这篇已经选定的稿件，使用这个音色生成配音。”网页负责展示和交互；后台负责检查条件、调用模型和保存结果。

第二层：Agent 协作——把制作工作分成不同职责

项目定义了一个总控和四个专家角色。Agent 可以先理解为“带有职责和可用工具的软件角色”。

  • 总控 supervisor：安排步骤、检查依赖，知道现在应该做什么、哪里需要等你确认。
  • 文案 content：提出三个角度，生成候选稿和表达意图。
  • 质量 quality：组织检查，登记问题和审核结论。
  • 人物 avatar：处理人物、动作参考和数字人视频相关任务。
  • 声音 audio：处理朗读表达、配音和音频检查。

这些角色体现软件职责分工，不要求每个角色各占一台服务器或各用一个不同的大模型。

当前实现边界

代码默认采用规则驱动的调度方式，内容工具可以另外调用真实模型。不能把这张图理解成“五个大模型已经能完全自主地把任何视频做完”。例如，当前视频原片的视觉审核明确需要人工参与；存在 quality 角色，并不代表系统已经能自动看懂所有画面问题。

第三层：业务执行与门禁——决定现在能不能做

“门禁”就是前置条件检查。生成数字人视频前，要检查人物是否确认、稿件是不是当前版本、配音有没有试听确认、视频路线是否选好，以及费用是否在允许范围内。

这些检查由程序执行。即使 Agent 说“准备好了”，也要满足实际条件，才能进入后续执行。

状态机

规定任务有哪些状态，以及怎样变化，例如排队、处理中、等待确认、成功、失败。没有视频文件时，任务不能直接成为“成功”。

幂等

尽量识别同一件事的重复请求。例如连续点击两次生成，应该复用同一次任务，避免重复生成和重复计费。

预算预留

提交前先确认额度，并为这次调用登记预算，避免多个并行任务同时花掉同一笔额度。最终还需要按真实结果核对费用。

unknown 对账

请求发出后连接断开，可能无法确定远端有没有收到、有没有完成。应先查询原任务，再决定下一步。

对应你之前遇到的错误

“作业结果尚未确认，请先查询原作业”表达的是：不能只凭通信失败，就判断远端没有执行。某一次请求到底有没有提交，需要结合它的作业编号和日志判断。这个机制的目的是避免不确定时重复提交。

第四层：Skill / MCP / 记忆——规定怎么做、能用什么工具、记住什么

  • Skill：业务操作规范，例如怎么写口播稿、怎么检查人物。
  • MCP / 工具通道：让 Agent 通过约定接口使用能力。
  • 工具白名单：只开放角色需要的操作，例如文案角色不能任意更改发布状态。
  • 记忆：保存人物设定、历史内容和经过审核的经验，方便下次检索与复用。
  • checkpointer：记录执行到哪一步，为流程恢复提供依据。

这里的“记忆”主要是存储和检索记录，不代表每次使用都会重新训练一个模型。记录流程进度也不自动等于所有外部作业都能够恢复；后者还需要持久化作业状态和结果核对机制。

第五层：Provider / Worker——真正执行具体任务

Provider 是外部能力供应商，例如 DeepSeek、MiniMax、OmniHuman。Worker 是接收任务并执行的程序，例如云端 Worker 接到字幕任务，调用对应模型生成识别结果和时间轴。

Worker 会组织模型运行、接单和返回结果。它不等于大模型，也不等于 GPU；GPU 是它执行某些计算时使用的硬件资源。

第六层：数据与媒体——保存正式记录和实际文件

系统保存两类东西：一类是业务记录，包括作品信息、选定稿件、任务状态和审核结论；另一类是媒体文件，包括人物图片、音频、原片、字幕、封面和最终视频。

文档中的“证据”，指实际文件、检测报告、供应商任务编号、审核记录等可核验材料。它们用于证明任务实际产生了什么结果。

再理解一步：为什么资产要保留版本和父链？

它要回答：“这条成片使用了哪张人物图、哪版稿件、哪段配音？”假如把第一版稿件改成第二版，旧配音和旧字幕可能已经不适用。记录每个产物从哪些输入生成，有助于识别哪些结果已经过期，避免把不同版本混成一个交付包。“资产不可变”强调保留历史版本，产生新版本时不要悄悄覆盖旧版本。

汇报时可以这样说

我们把职责分成入口、协作、业务检查、工具与记忆、执行能力、数据资产六部分。AI 负责适合生成与判断的工作，程序负责状态、预算和前置条件，关键质量环节由人工确认。

03

对应原汇报第 3 块 · 数据流与路线

一条 45 秒视频，是怎样一步步做出来的？

沿着一次制作过程看数据流，比先记住所有技术名称更容易。每一步都要知道输入、结果和下一步的依赖。

  1. D01

    建立作品，确定人物

    填写主题、受众、时长等要求，系统建立作品记录，再关联这次使用的固定人物。我们的例子是“45 秒办公效率技巧，固定女主播讲解”。

    Work 是这一期作品的总档案；Task 是围绕作品执行的一次制作任务；AgentWorkItem 是分给某个角色的一项具体工作；AvatarIdentity 是固定人物的身份档案。这些记录把后面的稿件、配音和视频关联在一起。

  2. D02—D04

    准备内容，三稿选一稿

    系统根据主题、关键词和可选资料，生成三个角度的候选稿，再检查重复、表达和事实风险，由你决定采用哪一篇。

    当前实现边界

    当前内容流程主要使用你提供的资料和内部历史，不具备自动搜索全网资料的能力。涉及产品参数、统计数字等具体事实时，需要有可核对的资料。

  3. D05—D06

    准备人物与最终配音

    人物侧准备衣服、背景和动作参考；声音侧生成配音。TTS 就是“文字转语音”，项目中主要由 MiniMax 承担。

    你要试听并确认最终配音，因为数字人的嘴型和字幕出现时间都会依赖它。如果重做某句话，让停顿变长，旧嘴型视频、旧字幕时间轴就可能需要重新生成。这就是“最终音频确认并冻结”的含义。

  4. D07

    选择数字人视频生成路线

    两条路线的共同目标是：让选定的人物讲出已经确认的配音。选择路线决定具体由谁执行、需要什么输入，以及费用和运维方式。

    路线一 · OmniHuman

    将人物图片和配音交给外部视频服务，得到音频驱动的人物视频。可以理解为：“把选定的人物和录好的声音交给供应商，请它制作说话视频。”

    项目负责素材上传、费用确认、任务查询和结果下载。

    当前限制

    当前接入要求输入音频严格小于 60 秒，达到或超过 60 秒会在提交入口阻断。当前流程不会自动把长音频拆段生成。长内容分段、拼接与质量验收，需要单独落实后才能作为可用能力汇报。

    路线二 · M2

    LivePortrait 根据人物图和动作参考，生成表情、头部运动等动作底片；MuseTalk 根据确认后的配音，调整底片中的嘴型。

    人物图 + 动作参考 → 动作底片 → 配音驱动嘴型 → 口播原片。

    原汇报所说的“本地 GPU”，更准确地理解为“我们自己管理模型的 GPU 路线”。当前实际 GPU 位于算力云。

    它的能力受模型与动作参考限制，不能理解成输入任意身体动作描述，就一定可以生成。

    为什么源码里还能看到 OmniHuman 分段函数？

    代码仍保留对历史分段台账的兼容逻辑，但当前提交入口统一检查整轨时长，并按单段提交。函数存在不等于当前产品已经开放长视频自动分段；阅读实现时需要顺着当前入口和实际调用路径判断。

  5. D08—D09

    生成字幕时间轴，审核原片

    ASR 是语音识别，回答“这段声音说了什么”；Forced Alignment 是强制对齐，在已经知道正文的情况下，回答“这些字分别在声音的什么时间出现”。

    例如正文是“今天分享三个技巧”，对齐结果要告诉系统：这句话从第几秒开始、到第几秒结束。这样后期才能在合适的时间显示文字。

    项目使用 Qwen3-ASR 和 Qwen3-ForcedAligner 处理这些工作。原片审核还要检查人物是否一致、嘴型是否对上声音、表情动作有无异常，以及音轨是否保持为确认过的那一条。当前视觉质量需要人工审核；若以后引入分段流程，还需要检查段间跳脸、断音等问题。

    字幕处理与视频生成，在输入条件满足时可以并行。最后的后期制作要等两边都准备好。

  6. D10

    后期制作，把原片变成正式成片

    有了原片、配音和字幕时间轴，还要处理字幕排版、画面规格、音量、封面和编码。这里主要使用 FFmpeg 等媒体工具。

    “确定性 Worker”强调这些操作由明确程序流程控制，例如按指定分辨率输出、按时间轴加字幕。它不意味着所有 AI 模型每次都会产生完全相同的结果。

  7. D11

    形成交付包

    交付包包含最终视频、字幕文件、封面、标题简介标签等作品信息、质量报告，以及文件清单 manifest。

    manifest 类似装箱单，说明包里有哪些文件；SHA-256 / hash 类似文件指纹，用来检查文件是否发生变化。文件指纹能帮助确认“是不是同一份文件”，不能证明“内容质量一定好”。

  8. D12

    保存经过审核的经验

    例如某种字幕字号在手机上更清楚，某个动作参考容易出现异常，可以形成经验记录，为下次制作提供参考。失败输出和未经验证的判断，不能直接变成以后都相信的规则。

交付完成和抖音发布，是两件事。

当前发布使用专用 Chrome 和浏览器适配器，并需要你确认。提交到平台后，还要分别核验平台受理、审核和公开状态；本地出现“上传完成”，不能直接代表已经公开发布。

汇报时可以这样说

一条作品从人物和文案开始，确认最终配音后进入视频与字幕制作，再经过原片审核和后期包装形成交付包。每一步保留输入和结果关联，关键输入一旦变化，就重新检查下游产物是否仍然有效。

网页状态与正式记录，为什么要分开？

Vue 构建你看到的页面；TypeScript 帮助开发者提前发现数据类型和代码错误；Pinia 管理当前页面正在使用的状态，例如选中了哪个人物；Vite 用于运行开发页面和前端打包。

页面状态不能替代数据库记录。要让刷新页面后仍能找回选定人物和稿件，就需要后端保存正式记录。

后台为什么同时提到 Python、FastAPI 和 Pydantic？

它们是不同层次的工具：Python 是后台主要编程语言；FastAPI 提供接收操作请求的接口；Pydantic 检查请求和数据是否符合规定格式。例如某个输入必须是有效任务编号、时长必须是数字，可以通过明确规则检查。

数据库、队列、对象存储，为什么不能只选一个？

数据库保存正式业务记录：这是谁的作品、到了什么状态。SQLite 是本地数据库文件，适合当前单用户形态；PostgreSQL 更适合数据库独立部署、多个服务共同访问，以及更复杂的并发和运维需求。

队列安排谁先执行：多项任务竞争 GPU 时，需要排队、领取和重试。Redis 可以参与队列、锁和缓存，但不能单独替代完整业务账本，也不会安装后就自动解决任务恢复。

对象存储保存大文件：它相当于供多台机器使用的媒体仓库。项目已接入向火山 TOS 上传 OmniHuman 输入素材的能力；整套媒体资产统一迁移到对象存储，仍属于后续改造。

媒体工具分工很具体

  • FFmpeg：处理、合成、转换音视频。
  • FFprobe：读取分辨率、时长、编码等媒体信息。
  • libass：按照字幕样式渲染文字。
  • Pillow：处理图片和封面。

监控系统回答：“出了问题，怎么知道卡在哪里？”

Prometheus 收集失败数量、队列长度等数字；Grafana 把它们显示成图表；Loki 汇集和查询日志；OpenTelemetry 帮助串起一次任务经过多个服务的过程。

选型表不等于安装清单。

这些监控工具和部分数据组件属于生产建设目标。汇报里出现名称，不能直接解释为已经全部安装，也不能代表已经完成正式压测。

汇报时可以这样说

前端负责操作体验，Python 后端承接业务规则，外部模型和云端 GPU 负责生成，媒体工具完成后期。当前以 SQLite 和本机文件为基础，后续按并发与可靠性需要引入独立数据库、队列、统一对象存储和监控。

对应原汇报第 5 块

性能与容量：系统接得住多少，视频做得有多快

这一块同时讲接口速度、GPU 产能和成片质量。先分清它们分别在测什么，才不会把“很快收到任务号”理解成“很快拿到视频”。

目标与待测项

原汇报将当前 QPS / P99 标为 NOT_RUN，没有可引用的现状实测。表中的 5、20、50、100 QPS，以及 SSE 连接数和 GPU 排队时间，属于建议压测门槛。下面的互动数字是帮助理解的假设算例，都不是本项目已经达到的成绩。

1. 接单速度和做完视频的速度，要分别计时

你点击“开始制作”后，系统先检查输入、版本和预算，把任务登记下来，再返回一个 job_id。这个号码相当于取件号：表示系统知道你要做什么，也能让你随后查询进度。此时，GPU 可能仍在处理前一条视频。

API 受理耗时

从请求进入后端，到返回任务号。原验收规范要求创建接口 P95 ≤ 2 秒、查询接口 P95 ≤ 1 秒；测量条件是记录本机配置、1 个运行任务、10 个同时查询客户端，至少采集 100 次创建/查询。

它回答的是：“点击以后，系统多久给我一个可靠回应？”

端到端耗时 E28

从任务受理，到用户能够预览、下载合格包。这里包括排队、生成、审核，以及等待用户选稿、试听和确认的时间。

它回答的是：“从我下单到东西真的能用，总共等了多久？”规范目前没有承诺每条视频固定几分钟完成。

因此，不能看见“创建接口 2 秒”就认为“视频 2 秒生成”。也不能只展示模型推理时间，忽略上传、排队、审核和用户等待；需要同时报告这些阶段，才知道真正慢在哪里。

2. QPS：每秒有多少请求，不是每秒有多少条视频

QPS 是每秒请求数。比如 10 个客户端，每个客户端每秒查询 2 次进度，就会带来 20 QPS 的查询请求。这些请求大部分只是在问“做到哪一步了”，并没有新生产 20 条视频。

动手算一算：多少次查询，会产生多少 QPS？

假设每个客户端以固定频率查询进度；这是请求量演示，不测量当前系统。

50 QPS 不能说成每秒生成 50 条视频。控制接口能够很快接收订单，并不代表后面的 GPU、云模型、审核和后期有同等产能。查询接口与创建接口也要分开统计，不能靠大量便宜的查询请求把创建能力“平均”得很好看。

3. P95 / P99：看大多数人和少数慢请求分别要等多久

把同一类请求的耗时从短到长排序，P95 取 95% 位置的值，P99 取 99% 位置的值。它们关注等待时间的分布；平均数可能被大量很快的请求拉低，掩盖少数用户等得很久的情况。

假设算例 · 非实测

有 100 次创建请求，排序后第 95 次耗时 1.6 秒，第 99 次耗时 3.5 秒，那么 P95 = 1.6 秒、P99 = 3.5 秒。可以说“至少 95% 的样本在 1.6 秒内完成”，不能说“所有请求都在 1.6 秒内完成”。

4. 并发客户端与 SSE 长连接：有多少人同时看进度

“100 个并发客户端”只说明有 100 个客户端同时活动。每个客户端多久请求一次，才决定它们制造多少 QPS。假设各 10 秒查询一次，平均约 10 QPS；假设各秒查询一次，才约 100 QPS。

SSE 可以理解为浏览器和服务端之间一条持续开着的进度广播通道。服务端有新进展时，直接推送“开始生成”“审核完成”等事件，浏览器不需要一直重复询问。

20 条 / 500 条长连接

原汇报建议一期同时维持 20 条、二期 500 条 SSE 通道。500 条连接不等于每秒新建 500 条连接，也不等于 500 个 GPU 视频作业同时推理。

事件送达 P95 ≤ 1 秒

衡量“服务端产生进度事件”到“浏览器收到事件”的时间。P99 ≤ 3 秒也是建议值。事件流水号 seq 用于发现漏消息、去重，并在断线后接着补看。

“心跳”用来确认连接还活着；“背压”是在接收方来不及时控制发送速度和缓冲区；“事件保留窗口”规定断线后多长时间内还能补回旧进度。它们保证页面能可靠展示真实进展。

5. GPU 产能：一张卡每分钟能完成多少实际作业

jobs/min 是每分钟完成的作业数。首先要定义一个 job 代表什么：是一个 motion 阶段、一个 lipsync 阶段，还是一条完整视频。M2 的两个阶段分别成功，不能直接算成两条可交付成片。

假设算例 · 非实测

假设某种作业独占一张 GPU 10 分钟，理想上限约为 1 ÷ 10 = 0.1 job/min，也就是每小时 6 个这种作业。实际还受加载、传输、排队和失败返工影响，完成作业也不代表质量审核已通过。

原汇报的容量公式是一种粗估：所需 GPU 数 ≈ 窗口内任务数 × 每任务 GPU 分钟 ÷ 窗口分钟 ÷ 目标利用率。公式里的任务数量必须与时间窗口对应，不能随意把“峰值每秒请求数”代进去。

假设任务可分配到同类 GPU，每项任务的全部 GPU 阶段合计占用指定分钟数。

6. “GPU 排队 P95 ≤ 3 秒”必须写清负载条件

原汇报按 queued_at → started_at 衡量排队时间，即“进入队列”到“真正开始执行”。它与“把任务写进队列只花几毫秒”是两种不同耗时。

假设一张 GPU 做一个任务要 10 分钟，又有两个任务同时到达。即使后端马上收单，第二个任务通常也得等前一个结束。此时无条件要求排队 P95 ≤ 3 秒，就与单 GPU 串行的实际资源限制冲突。

这项指标应理解为需要重新限定条件的压测建议：例如低到达率、预留执行槽或足够多 GPU。验收前必须明确 GPU 数、任务时长、到达方式、冷热启动、队列上限与限流策略。GPU 很忙时让任务明确排队，是正常业务状态，不应伪报失败或开始运行。

7. 200ms 测的是音画偏差；下载首字节测的是传输开始

嘴型 / 字幕边界 P95 ≤ 200ms

衡量嘴部动作与语音事件、字幕出现结束与对应语音之间的时间差。30fps 视频中 200ms 约为 6 帧。它属于成片质量，详细测法见第 7 块。

下载首字节 ≤ 500ms

表示用户请求下载后，很快收到文件的第一部分，不代表整个大视频在 500ms 内传完。完整下载还取决于文件大小、出口带宽和用户网络，应单独压测。

18/20 合格交付与 5/5 单日生产窗口也是性能页展示的重要数字，但属于真实生产验收。它们需要完整的任务、质量和成本证据，第 7 块会解释分母与通过条件。

生产级部署：放到哪里运行，断了以后怎么恢复

部署图讲的是机器、网络、数据和运维的责任分工。先让当前单用户工作台稳定运行，再补齐多人、公网和长期运行需要的能力。

1. 现在：Windows 工作台连上云端 GPU

Windows 主机承载工作台页面、FastAPI 后端、SQLite、媒体目录和 FFmpeg 后期，也保留专用 Chrome 发布会话。当前发布流程需要可见浏览器，由用户最后确认，所以需要已登录的交互式桌面。

Linux GPU Worker负责 M2 以及适用的 ASR、字幕对齐等计算。Windows 通过 SSH 隧道访问它：可以把隧道想成两台机器之间的受控通道，把本机 18080 转发到远端 Worker 的 8080。健康检查要看到 motion / lipsync / asr / align 四阶段，仍需各阶段实际调用证据才能证明业务效果。

部署文档推荐“单用户、单机、仅本机访问”。当前后端没有用户认证，8000 / 5173 / 18080 不得直接开放公网入站。同一运行目录也不能启动多个后端，或让多台主机同时共享写入。

2. “自动恢复”至少有四种含义，不能混说

隧道断开后重新连接

长期隧道配置使用用户登录任务维持 SSH 转发，支持断线重连。它恢复的是网络通道；不能因此宣布前端、后端、云端实例和旧推理任务全部自动恢复。

Worker 进程退出后重新启动

已安装的恢复服务提供单实例守护和退出后的退避恢复，本机 start.ps1 会做安全 ensure。guard 是项目的守护机制；它不等于已经部署了 Linux 的 systemd 服务。

云端机器关闭后重新开机

项目启动触发 Worker 检查和恢复，不意味着能够自动把已关机的付费云实例开起来，也不意味着实例一开机就会自行启动全部项目。云实例可达是后续恢复的前提。

旧作业在重启后继续处理

当前 Worker 的作业表保存在内存，重启会丢失内存里的作业索引、状态和排队记录，已完成与未完成作业的索引都会受影响。媒体文件可能仍保存在磁盘上，但不能仅凭文件存在就自动恢复旧作业；持久化作业账本与重启对账仍需补齐。

部署文档还给出了“用户登录时运行”的本机工作台任务计划方案。该方案、已配置的隧道登录任务、Worker guard 各自负责不同范围。解释“开机恢复”时，应明确哪些任务已经安装、什么事件会触发，以及恢复的对象是进程、通道还是业务作业。

服务活着，不代表任务恢复了。如果供应商已经收到了请求，本地却没拿到回执，系统应按原任务 ID 核对，保留 unknown 状态与费用证据。直接重新提交可能生成两条视频、扣两次费。

3. 下一步：把数据库、队列、文件和执行进程分开管理

一期把很多组件放在一台工作台上，容易上手。用户增加后，最先需要解决的是并发写入、任务不丢、文件可找、费用可对账，以及某台机器出问题时如何恢复。

  • PostgreSQL：保存作品、任务、选择、审批和费用等业务事实。迁移的意义在于可验证的事务、并发与恢复能力，不能只换一个数据库名字就算完成。
  • 持久化队列与租约：把未完成工作记在可恢复的位置；Worker 领取任务时占用一个有期限的执行权。进程失联后先核实原任务状态，再决定续跑或人工处理。
  • 对象存储：集中保存图片、音频、视频和交付包，让文件独立于某一台工作台。数据库保留位置、版本、来源与哈希，以便证明取到的是哪份文件。
  • 独立 Worker：生成、后期和发布按各自资源与风险调度。发布浏览器仍保留交互式执行节点，不能因为其余组件上了服务器就假设可以无人值守投稿。

4. 部署图里的缩写，各自解决什么问题

HTTPS 与反向代理

HTTPS 加密浏览器与入口之间的传输。Caddy / Nginx 等反向代理提供统一入口，把页面和 API 请求转到内部服务。只开放 443 并不能替代用户认证和权限检查。

SSO 与 RBAC

SSO 是统一登录，解决“你是谁”；RBAC 是按角色分配权限，解决“你能做什么”。例如能看进度的人，不一定可以修改预算、管理供应商或确认发布。

签名 URL

带有效期限与受限权限的下载地址。用户在有效期内可以访问指定文件，无需把整个媒体目录公开。它适合预览、下载和 Worker 受控取文件。

PITR

数据库的时间点恢复。除了保存备份，还连续保留恢复所需日志，以便回到某个较精确的时间点。它不能自动恢复遗漏备份的视频文件，所以数据库和媒体需要一致的恢复策略。

Secrets Manager

集中保存与发放服务密钥，控制哪些进程能读取，并支持轮换。密钥、临时签名和浏览器登录会话不应混进普通日志、Agent 上下文或公开交付包。

灰度 / 金丝雀发布

新版本先承接少量受控任务，观察错误、质量和费用，再扩大范围。一旦异常能够回退；不是直接让全部生产任务承担新版本风险。

5. 监控要能回答“哪一条任务，卡在哪一步”

Prometheus收集可统计的指标，例如队列长度、任务失败数、GPU 利用率和接口延迟；Grafana把这些指标画成看板；Loki集中保存和检索日志；OpenTelemetry帮助串起一次任务经过的 API、Agent、Provider 和 Worker。

关联时使用 work_id / stage_id / provider_run_id。用户说“这条片一直没好”，运维就能沿这些 ID 找到排队记录、供应商回执、下载失败或审核结果。只有一个“服务健康”的绿灯，无法证明某条视频已经正确交付。

告警应对应可操作的问题，例如持续积压、GPU 长时间异常空闲、费用逼近上限、重复提交或任务受理未知。Runbook 则是出现这些问题时的处置说明，写清检查顺序、负责对象和恢复办法。

6. 备份的验收标准：真的恢复过，而不只是有压缩包

当前方案要求每日备份，并在另一目录做恢复演练。备份需要覆盖业务数据库、媒体与交付包，以及受控保存的配置和会话；秘密资料单独加密。SQLite 运行时直接复制一个数据库文件，可能遗漏写入中的数据，需要一致性备份。

恢复以后要实际检查作品列表、任务状态、成片播放和下载包。旧任务受理不明时继续对账。回滚也要核对代码版本与数据迁移是否兼容，不能只换回旧程序却让它读取不兼容的新数据库。

查看当前部署与二期改造依据

当前拓扑、用户登录任务、Worker guard、内存作业表及二期公网前置条件，见 部署方案 第 1、6、7、8、10 节。SSO、对象存储、完整观测平台等在本汇报中按目标能力理解；是否已经上线，应以对应配置、运行记录和恢复验收为准。

汇报时可以这样说

“现在适合本机单用户工作台，云端 GPU 负责重计算。隧道重连和 Worker 进程恢复已经有运维机制，但旧作业持久恢复、公网认证、队列与对象存储还需要进一步验收。生产化的关键，是机器或网络出问题后仍能找到任务、账目和文件。”

07

对应原汇报第 7 块

评估与验收：怎样证明视频真的可以交付

这一块定义“通过”需要哪些证据。接口能返回成功、模型生成了文件、用户拿到合格包、平台正式发布，是不同的完成程度。

1. L0 / L1 / L2：先讲清证据能证明到哪一步

  1. L0

    结构与契约：用模拟演习检验流程

    验证输入输出格式、状态转换、权限、预算、防重复提交、版本失效和故障处置。可以使用确定性的模型替身与新建合成夹具，做到便宜、可重复地发现程序问题。

    L0 即使产出可播放 MP4，也不能证明真人感、固定声音、嘴型质量或真实发布。把结构跑通与真实媒体质量分开，才能知道还欠哪类证据。

  2. L1

    真实生产：得到可以预览、下载的合格包

    在明确预算与调用范围内使用真实 Provider、真实人物与音频、真实后期处理，逐项通过质量门禁，并保存完整来源、费用、版本和审核记录。

    L1 的成功语义是“真实生产和就绪包通过验收”。当前 MVP 必须独立验证 OmniHuman 主链路；M2 是另一路能力，其通过不能代验 OmniHuman。完成 L1 也不代表已经在抖音发布。

  3. L2

    官方发布：有平台可核验的实际结果

    在具备官方权限及具体发布授权后，核对目标账号、作品 ID、官方回执、受理和审核/公开状态。上传成功、HTTP 200、打开发布页面或人工回填都不能自动算正式发布通过。

    如果官方流程要求用户确认，结论应如实写“官方渠道人工确认发布”。L2 不是当前 V1 下载闭环的完成条件；其权限阻塞也不能抹掉已独立通过的 L1。

2. PASS / FAIL / BLOCKED / NOT_RUN：通过、失败和没测不能混

PASS · 通过

需要的样本、测量和证据都齐全，且所有适用硬要求与本批冻结判据都满足。不能只凭 Agent 说“完成了”就记通过。

FAIL · 未通过

已经执行验证，发现违反硬要求或本批确定的门槛。保存失败证据、明确返工范围，修复后再测受影响部分。

BLOCKED · 前提缺失

例如缺少权限、授权预算或实际能力，导致当前无法完成这一项。它是需要说明原因的阻塞，不是成功。

NOT_RUN · 尚未执行

有测试计划，但没有执行证据。文档写了阈值、代码里存在接口或已有一次历史样片，都不能自动把它改为通过。

报告应同时交代全部适用项目、已测数量与未测/阻塞数量。如果 69 项只测了 10 项，即使这 10 项全过，也只能报告“已测 10 项通过，剩余范围及状态另列”，不能只留一个“100% 通过”让人误以为整个系统已经通过。

3. 69 项用例、11 步流程和 D01–D12，分别在数什么

69 项是验收清单数量：原有 61 项加 8 项工作台用例。清单包括结构、生产和未来发布等适用范围；它不是已通过数量，也不意味着每一项都在 V1 当前范围内。

11 步是用户从建作品到预览下载的生产流程，其中包含可以并行的 TTS / 人物准备，以及二选一的视频路线。D01–D12是更细的数据交接编号，不新增 12 个业务阶段；D12 额外说明审核经验如何回流到长期记忆。三套编号用途不同，所以不能直接比较数目。

4. 内容与声音：不是“读得顺”就可以交付

E02 · 三稿新意 ≥ 4/5

先冻结 10 个主题，每个主题写 3 稿，由 3 人盲评，并写出稿件相对历史增加了什么问题、论证或案例。每一稿单独判断，三稿不能只是同义改写。

4/5 是预设的人评档位与建议门槛，不能把两篇好稿和一篇差稿平均成三篇都合格。

E04 · 关键事实支持 100%

把稿件中的关键可验证断言逐条列出，对照用户资料或已核有效来源。只有完整支持才计入分子；模型自己说“这是真的”不构成事实核验。

没有事实断言的纯观点稿应写“不适用：无关键事实”，不能为了好看填 100%。

E07 · 固定声音与版本一致

检查实际音频是否使用本作品确认的音色、模型与参数版本，并由人对照基准听。配置中的声音 ID 一样，不代表听感一定没有漂移。

正确声音引用要求 100%，确认换声或漂移为硬失败。

E08 · CER ≤ 2% 与关键读音全对

CER 是“替换、删除、插入的字符数”除以批准朗读文本字符数。假设 200 字有 4 个普通字符错误，CER 为 2%；这只是算例。

人名、术语、数字必须准确，不能用整体 CER 达标掩盖关键误读。漏句、重句、额外句或把控制标记念出来都要处理，不能只改字幕藏住声音错误。

5. 身份、嘴型与字幕：逐片看，保留问题时间点

E10 身份漂移为 0：换衣、换背景、转头或后期增强以后，仍须是所选人物。审核会看首中末、转头和剪接处；如果看不清或无法判断，要进入复核，不能自动通过。

E14 嘴型同步：两人逐帧标注每片至少 30 个有效闭唇、圆唇等事件，覆盖首中末与切段位置。计算 |视频事件时间 − 对应音频事件时间|，建议中位数 ≤ 120ms、P95 ≤ 200ms。

假设算例 · 非实测

某个发声事件发生在 10.000 秒，画面对应嘴部动作在 10.150 秒，偏差就是 150ms。对 30 个偏差排序，P95 取第 29 个。中位数反映多数事件，P95 关注更慢的一部分；仍需完整观看，因为持续明显错位属于硬失败。

E16 字幕：对照批准正文与朗读映射，要求应出现的正文覆盖 100%，没有严重漏错重句、越界或关键遮挡。两人标注至少 30 个字幕首尾边界；不足时全测并写明数量，边界绝对偏移 P95 建议 ≤ 200ms。

嘴型准、字幕准和音轨保持是分别验收的事情。输入给模型的音频正确，不代表模型输出没有变声、改读音或改变时长。剪辑一旦改变，还要重新核对最终时间轴；不能把原片审核通过直接继承给剪辑后的文件。

6. 媒体技术质量：文件符合格式，还要真的听得清、看得完

E17 · 1080×1920 / 30fps CFR / H.264 + AAC

1080×1920 是竖屏尺寸；30fps CFR 表示每秒固定 30 帧；H.264 是视频编码，AAC 是音频编码。通过 FFprobe 和完整解码检查，不能只看文件扩展名或平均帧率。

E18 · −14 LUFS ± 1

LUFS 衡量整体感知响度，目标是各片听起来音量稳定。还要求 true peak ≤ −1.5dBTP，避免瞬时过载，并核对无截字、首尾与剪点完整。

建议音画总时长差 ≤ 250ms，是检查视频与对应音轨的总长度是否接近；它不等于嘴型误差 ≤ 200ms。两条轨道一样长，也可能从头到尾错位。最终成片还要排除未解决的异常黑帧、冻结、贴片嘴和融合缺陷。

7. 18/20：20 个真实任务里，至少 18 个交付合格包

E25 要先登记 20 次真实生产任务，再计算 合格包任务数 ÷ 已启动任务数。建议目标至少 18/20，也就是 90%。只有真正启动的独立任务才能进入这批统计，同一任务重试不增加分母，重复下载同一视频也不增加成功数。

  • 失败、阻塞和启动后取消都留在分母：不能只挑成功的算。启动前撤销另列，不计为已经启动的 20 次任务，也不补抽替换；原登记批次因此不足 20 个已启动任务时，只报告实际数量，不断更换样本不能制造达标结论。
  • 返工可能帮助原任务最终合格：但返工费用、等待和失败原始证据必须保留，不能把它说成一次就成功。
  • 不足 20 次只作阶段观察：不能凭一条成功样片推算“90% 稳定交付”。不同路线分别报告。
  • 失败产物要被挡住：允许总体有失败任务，不代表允许把不合格的视频交给用户。
假设算例 · 非实测

20 个已启动任务中，17 个合格、2 个失败、1 个启动后取消，交付率是 17/20 = 85%。删除后面 3 个再写成 17/17 = 100%，会掩盖实际生产损失。

8. 5/5：一天内约定的窗口里，完成五条约 60 秒内容

E26 的“5/5”指五条任务全部完成，不是连续五天。先冻结一天的生产窗口、5 条独立稿件、约 60 秒的允许时长范围、路线和预算，再按真实排产完成合格包。使用当前 OmniHuman 路线时，允许范围和最终输入音频还必须满足严格小于 60 秒；“约一分钟”的验收描述不会取消入口限制，也不代表已经具备自动分段能力。

比如“09:00–18:00”只是可采用的窗口示例，文档没有统一承诺 8 小时或 24 小时。排队、用户确认、重试、GPU 占用与空闲费用都需要记录；联合验收还覆盖一次可控恢复。

五段 10 秒短片不能折算五条约 60 秒成片；4 条合格、1 条超窗不能说 5/5。失败任务不能被替换后沿用原批通过结论。单天通过也不能证明长期稳定，5/5 与 18/20 各自回答产能和稳定性问题，不能互相替代。云路线完成五条，也不能据此宣称本地单 GPU 产能通过。

9. E27 成本与 E28 耗时：把失败和等待也算进去

每个合格包的成本是批次全部实付支出除以合格包数。文本、图片、TTS、云视频、GPU、存储传输，以及失败返工和适用的空闲支出都要考虑；估价、预留和实付分开记录，不重复计算同一 GPU 费用。

假设算例 · 非实测

这一批总共花了 1,000 元，最终有 18 个合格包，那么约为 1,000 ÷ 18 = 55.56 元/合格包。不能只拿 18 次成功调用的费用去除；如果没有合格包或账单缺失，也不能填“0 元”。

单包成本上限仍需确定，总支出不超本批授权预算是硬门槛。E28 则从受理计到可预览下载，完成任务报告中位数/P95，并拆排队、生成、审核和用户等待；失败未完成数与已等待时长另报。不能只留下最快成功样本。

10. 为什么不能用综合高分掩盖一个硬失败

声音很好听，不能抵消一句无证据的关键事实；人物很好看，不能抵消嘴型持续错位；其他 19 个指标达标，也不能抵消错误人物、泄密、超预算或漏放严重缺陷。

因此验收分两类：硬门槛必须逐项满足，失败就隔离产物、阻止下游；建议阈值在测试前冻结为本批标准。待标定项目先做校准再验保留集，纯观察项只报告数值，不冒称“达标”。没有测到的值也不能填 0 来假装没有问题。

11. 已有历史证据：协议测试与真实出片要分开讲

已记录的有限证据

Worker README 记录了两类不同结果：13 项端到端协议测试使用“真实 Worker 服务 + 假 runner”，另有 2 项启动校验；同一文档还记录了两次独立的真实模型阶段出片。两类证据不能混称为一次完整生产验收。

真实 motion 阶段

产出约 23.200 秒动作底片，提交到终态约 126.7 秒。它说明该次动作阶段确实执行并出片，仍需独立核对正式质量要求。

真实 lipsync 阶段

产出约 23.187 秒口播原片，用时约 217.9 秒。原记录还核对了音轨，但只有两帧目视抽查，不能替代全片身份、自然度与嘴型正式验收。

这些是两次串行阶段运行；不是生产 P95 / QPS、重启恢复或多作业排队成绩，也不是 18/20、5/5 或完整约 60 秒交付通过。短片耗时不能直接按比例外推一分钟成片，因为加载、分段、合成与审核并不一定线性增长。

查看指标、样本与历史证据依据

详见 验收标准与测试方案 的第 2、4 节及 AC-NFR-04、AC-AG-10；11 步与数据交接编号见 端到端技术流程与模型选型地图。历史阶段耗时和明确未验证事项见 M2 Worker README 的“已验证 / 未验证”。

汇报时可以这样说

“验收看的是证据能走到哪一层。L0 证明程序结构，L1 证明真实可交付，L2 才证明官方发布。18/20 要保留失败分母，5/5 要在规定窗口内做出五条约一分钟的合格视频；已有真实短片说明路线有进展，还不能代表整套生产验收通过。”

08

对应原汇报第 8 块

落地路线：按依赖顺序把能力补成闭环

W1、W2–W3、W4–W6、W7+ 表达建议阶段顺序和粗略排期。它们需要结合人力、模型权限、预算与验收结果重新估算，不能当作已经开工的日历或确定交付承诺。

  1. W1

    先统一“什么才算一个有效交付包”

    作品、音频、原片、字幕、封面和质量报告都要绑定同一有效输入版本；manifest 记录文件清单、来源和 SHA-256 摘要。这里的摘要相当于文件指纹，用于发现错文件、被替换或传输损坏。

    Pydantic schema 定义接口可以接收什么字段、如何报错；幂等键保证用户重复点击或网络重放时，尽量回到同一个操作记录。验收应能阻止缺文件、过期审批、版本不一致或 Mock 冒充真实交付。

    阶段结果：包能被程序校验，人能预览下载，任何“就绪”状态都能追溯到对应文件和审核证据。

  2. W2–W3

    让 Worker 重启以后还能查清旧任务

    把进程内存中的作业记录迁移到持久化账本，补齐领取租约、心跳、异常退出、断线重连和未知状态对账。按实际宿主环境选择 guard 或受支持的服务管理机制，不能在不支持 systemd 的容器里只写一个服务文件就算完成。

    “死信队列”用来保存多次失败、暂时无法安全继续的任务，等待人工处理；有限重试必须区分查询、下载与可能再次计费的 submit。外部已经受理时先查询原任务，不能因为本地丢了结果就再买一次生成。

    阶段结果：通过真实适用的中断与恢复演练，任务不假成功、费用不重复、未知状态能说明白。进程能启动只覆盖其中一小部分。

  3. W4–W6

    迁移数据和媒体，再做受控压力测试

    逐步引入 PostgreSQL、Redis 与对象存储，验证事务、队列和文件引用在多进程下仍然一致；建立备份、恢复、签名下载与媒体保留策略，并把指标、日志和任务关联接起来。

    这些前提具备后，再按固定环境、持续时间、到达率与错误标准验证 QPS、P95、P99。测试报告要保留接口错误、GPU 等待、成功交付率和恢复结果，不能只截一张漂亮吞吐图。

    阶段结果：有能复核的压测报告、恢复报告和回滚办法；上线范围按验证结果扩大，而不是按组件安装数量扩大。

  4. W7+

    在真实闭环稳定后，再扩展多用户和多 Worker

    增加登录、角色权限、配额和用户之间的数据隔离，再按供应商、GPU 类型和预算调度任务。通过少量任务灰度验证新版本，具备跨节点恢复能力后逐步扩大运行规模。

    50 QPS 仍是控制面的建议目标，需要对应压测证据。平台发布作为 L2 独立验证，不能用新增平台入口数量代替真实交付或发布质量。

    阶段结果：明确多少用户、多少任务和什么故障范围已经验证，以及暂时不开放什么能力。

每个阶段都应能回答三个实际问题

交付了什么，用户怎样使用

例如可以下载真实合格包、刷新后还在同一个任务、服务器重启后能找回作业。描述看得见的行为，比只列技术组件更容易判断价值。

用什么证据证明，失败怎么办

给出实际样本、版本、费用、耗时和检查记录；说明失败如何隔离、谁来复核、如何回滚。还没测的范围明确保留为未执行或阻塞。

第三个问题是下一阶段依赖什么：例如真实质量门禁、权限、授权预算和持久化恢复。依赖没解决时调整排期与开放范围，不能为了追赶“第几周”把未验证能力包装成已完成。

整份汇报描述的方向是：先把一条作品从输入到合格包做成可追溯的闭环，再让任务和费用经得起中断，最后扩大用户、GPU 和平台范围。“工业级”最终需要持续运行与故障证据支撑，文档本身不产生这些成绩。

回到原汇报与实施资料

本节对应 原汇报落地路线。具体任务依赖以 开发实施计划、当前代码和逐项验收记录为准；当前运行边界以 部署方案 为准。

汇报时可以这样说

“这是一条按依赖推进的路线：先保证交付真实完整，再补任务恢复，再迁移数据与做压测，最后扩多用户和平台。周数是规划标签，真正进入下一阶段要看证据，不靠时间到了就自动算完成。”

遇到缩写，回来查一句话解释

术语随手查

不用先背技术名。知道它解决哪件事，就能继续往下读。

API / 接口
网页与后台之间约定好的办事窗口，例如提交任务、查询进度。
前端 / 后端
前端展示页面和接收操作；后端检查业务条件、调用能力并保存正式记录。
Agent / 智能体角色
承担特定职责的执行角色，可按规则或模型决策调用受限工具；角色数不等于服务器数。
DeepAgents / LangGraph
组织角色、工具调用和流程状态的框架；具体生成能力由模型或工具提供。
Skill / 业务技能
某项工作的操作规范，例如口播写作或固定人物的审核要求。
MCP / 工具通道
按统一约定把工具提供给智能体使用；实际权限由白名单和业务校验控制。
Provider / 能力供应商
通过接口提供模型服务的平台，例如 DeepSeek、MiniMax、OmniHuman。
Worker / 执行程序
接收具体任务、调用模型或媒体工具、记录并返回结果的程序。它不等于 GPU 本身。
GPU / 显卡计算
适合大量并行数值计算的硬件资源；本项目的自管模型当前运行在租用的云 GPU 上。
推理
给已经训练好的模型输入资料，让它生成或识别结果；并不是重新训练模型。
TTS / 文字转语音
把批准的文字转换为配音；项目主要使用 MiniMax。
ASR / 语音识别
听一段声音，识别它说了什么。项目接入 Qwen3-ASR。
Forced Alignment / 强制对齐
在已知正文的情况下，确定字词在音频中何时出现，用于字幕时间轴。
M2 / 自管 GPU 路线
先用 LivePortrait 制作动作底片，再用 MuseTalk 按最终配音对口型。当前 GPU 位于云端。
OmniHuman / 云视频路线
外部音频驱动人物视频服务；当前提交入口要求音频严格小于 60 秒，超限阻断。
Work / Task / Job
Work 是作品档案；Task 是制作任务；Job 通常是交给某个执行器或供应商的具体作业。
状态机
规定任务可以处于哪些状态，以及怎样从排队、执行或等待确认走向成功、失败等结果。
门禁 / Gate
动作执行前必须满足的条件，例如最终音频已确认、人物已审核、预算已授权。
幂等 / Idempotency
识别同一次操作的重复请求，避免反复执行；可靠范围取决于具体实现与持久化。
unknown / 结果未知
目前证据不足以确定外部任务的最终结果，需要查询原作业和费用记录，不能盲目重提。
版本 / 父资产 / 血缘
记录成片使用了哪版正文、哪张人物图和哪段配音，使结果可追溯并能识别旧产物失效。
hash / SHA-256
文件内容的指纹，用于检查是否还是审核时的同一份文件；不评价内容质量。
manifest / 交付清单
描述交付包有哪些文件及其大小、指纹和相关编号的清单。
SQLite / PostgreSQL
保存业务记录的数据库。当前使用本机 SQLite；独立部署的 PostgreSQL 属于后续目标。
Redis / 队列
Redis 可参与共享任务队列、缓存和锁；队列决定任务如何排队和被领取，不能替代全部业务账本。
JobStore / 作业账本
保存 Worker 作业状态和索引的地方。当前云 Worker 版本保存在进程内存中，重启可能丢失。
持久化 / checkpoint
把状态保存到可靠存储，而非只放在运行进程内；checkpoint 记录流程执行到哪一步。
租约 / 锁
控制任务或 GPU 在一段时间内由谁使用，减少多个执行者重复领取或争抢资源。
死信队列
保存多次执行失败、需要人工分析和处理的任务，避免无限重试。
对象存储 / S3 / MinIO / TOS
保存媒体文件的独立仓库。项目已有部分 TOS 素材桥接，统一媒体存储改造仍是后续目标。
签名 URL
带授权和有效期限的文件访问地址，常用于受控下载或向服务提供输入。
SSH 隧道
连接本机后端与云端 Worker 的加密转发通道。通道连通与 Worker 运行需要分别检查。
127.0.0.1 / 端口
127.0.0.1 指当前机器自己；端口用于区分这台机器上不同服务的入口。
ensure / guard / systemd
ensure 检查并在安全条件下拉起 Worker；guard 是当前自有守护程序；systemd 是另一种进程管理方案。
QPS / RPS
每秒请求数量。本汇报用于接口受理或查询吞吐，不能换算成每秒完成多少条视频。
P95 / P99
将耗时从小到大排序，取 95% / 99% 位置的值。它们不是平均值，也不是成功率。
SSE / 进度推送
服务端持续向页面推送进度的连接；长连接数量不等于视频生成并发数。
jobs/min / 端到端耗时
前者是每分钟完成的作业数，须定义作业范围；后者统计从受理到合格交付的全过程。
CER / 字错误率
相对批准朗读文本的替换、漏字、添字总数除以字符数；人名、术语、数字还需单独严格检查。
fps / CFR / H.264 / AAC
fps 表示每秒帧数，CFR 表示帧率恒定，H.264 和 AAC 分别是视频与音频编码。
LUFS / 响度
衡量音频整体听感响度的单位，用于控制成片声音水平，不是模型生成速度。
L0 / L1 / L2
依次验证程序与接口规则、真实生产交付、平台发布事实；不同层级的证据不能互相替代。
PASS / FAIL / BLOCKED / NOT_RUN
分别表示验收通过、实测不合格、缺前提受阻、尚未执行。未测不能当通过。
SSO / RBAC
SSO 是统一登录；RBAC 是按用户角色分配权限，例如制作、审核、管理。
备份 / PITR
备份保存可恢复副本；PITR 指恢复到某个时间点。需要实际恢复演练证明可用。
Prometheus / Grafana / Loki
分别用于指标采集、监控图表、日志汇集与查询；本项目完整监控平台属于后续目标。
OpenTelemetry / trace_id
串起一次任务经过多个服务的记录；trace_id 是用于追踪和定位问题的关联编号。
Secrets Manager / 凭据轮换
集中管理服务密钥并在需要时更换，避免凭据进入网页、日志或智能体上下文。
灰度 / 金丝雀发布
先让少量使用范围运行新版，观察正常后逐步扩大，降低更新影响范围。
