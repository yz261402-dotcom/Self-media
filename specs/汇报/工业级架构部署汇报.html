02 / ARCHITECTURE

总体架构：控制面、执行面、证据面分离

Agent 负责协作与决策建议，业务服务负责状态、预算、幂等和权限，确定性 Worker 负责字幕、后期、封面和交付包，媒体和证据保持不可变。

目标架构拓扑 Work 是根对象，所有派生资产保留父链
一期真实事实源仍是 SQLite 与本机 runtime；PostgreSQL、Redis、对象存储是二期生产升级目标，不能在当前汇报中写成已部署事实。
架构原则 生产稳定性优先
状态权威业务服务写状态、选择、审批、预算和交付清单，Agent 不直接写成功或发布。防止“模型说完成”替代事实状态
资产不可变图片、音频、原片、字幕、成片和证据保存 hash、父资产和版本。迟到结果不能覆盖当前指针
费用可对账提交前预留预算，外部未知状态先查原任务和账单，禁止盲目重试。幂等键覆盖提交、查询和回调
发布隔离生产包 ready 不等于已发布；抖音浏览器仍需要用户可见确认。发布单独建模，不混入生成状态机

03 / DATA FLOW

端到端数据流：确认点驱动的异步生产

作品、人物、稿件、音轨和路线都使用版本指针；TTS 确认是两条视频路线的共同前置，字幕对齐可与视频推理并行，最终统一汇合到交付包。

D01 · 需求进入作品

建作品 / 选人物

主题、受众、时长、预算 → Work、Task、AgentWorkItem、AvatarIdentity。

D02–D04 · 内容准备

资料登记 / 三稿 / 选稿

用户资料与内部历史查重 → DeepSeek 三稿 → quality 审核 → 用户显式选择。

D05–D06 · 音画准备

TTS 与人物并行

人物衣景与表演计划、MiniMax 音频报告；最终音频必须试听确认并冻结。

D07 · 路线门禁

选择 OmniHuman 或 M2

能力、预算、输入版本和音轨一致后才提交外部 Provider 或 GPU Worker。

D08–D09 · 质量证据

字幕对齐 / 原片审核

ASR 与对齐使用同一最终 TTS；审核身份、动作、表情、嘴型、声音保持和连续性。

D10 · 确定性后期

字幕 / 封面 / 成片

FFmpeg、libass、FFprobe、清晰度处理和封面由代码 Worker 执行，终审检查最终文件。

D11 · 交付冻结

PublishPackage / manifest

成片、字幕、封面、文案、AI 声明、质量报告与 SHA-256 清单一起冻结。

D12 · 经验回流

审核经验沉淀

只把经过审核的 MemoryCandidate 写入经验层，不能让失败稿自动成为长期事实。

依赖关键点：D05/D06 可并行；D08 在 D06 后可与 D07 并行；D10 等待 D08 与 D09；M2 重型任务按单 GPU 租约排队，Agent 并行不等于无限提交。

主路线 · OmniHuman 1.5

MVP 交付路线，固定人物图与已确认 MiniMax TTS 作为输入，直接生成音频驱动口播。

AvatarVariant + FinalTTS + PerformancePlan → OmniHuman → 原片审核 → 字幕 / 后期
云端 Provider音频 < 60s 门禁身体动作待实测

可选路线 · M2 本地 GPU

成本可控的本地路线，先用 LivePortrait 生成动作底片，再由 MuseTalk 使用同一最终音轨对口型。

AvatarVariant + ApprovedMotion → LivePortrait → MuseTalk + FinalTTS → 原片审核
单 GPU 租约需 Worker 四阶段健康不能代验 OmniHuman

05 / PERFORMANCE

性能与容量：区分现状、验收阈值和压测门槛

当前系统是单用户、异步长任务、单 GPU 串行形态。仓库没有可引用的 QPS/RPS 或 P99 实测，因此本节把 P95/P99 和 QPS 写成可执行的压测契约，而不是虚构成绩。

≤ 2 s创建接口 P95

已有 AC-NFR-01 建议阈值；只统计请求受理，不含真实生成耗时。

≤ 1 s查询接口 P95

任务状态、作品读取和进度查询；与生成时间分开。

≤ 200 ms嘴型 / 字幕边界 P95

E14 / E16 的媒体质量阈值；不是 API 延迟。

18 / 20合格交付率

真实任务窗口建议门槛；失败和返工不能用短片替代。

5 / 5单 GPU 日产窗口

约 60 秒内容连续 5 条，需真实生产证据。

NOT_RUN当前 QPS / P99

全仓库未找到可引用的现状实测，必须在二期压测后更新。

06 / PRODUCTION DEPLOYMENT

生产级部署：一期稳态，二期演进

部署设计围绕交互式发布、GPU 资源隔离、数据恢复和外部调用对账展开。公网部署前必须完成认证、持久化队列和秘密管理，不能把当前本机端口直接暴露出去。

推荐生产拓扑 一期可落地 / 二期可扩展
一期使用 Windows 本机工作台 + Linux GPU Worker；二期将控制面、数据层、队列和媒体层独立部署，发布浏览器保留交互式执行节点。
上线硬门槛 未完成即保持内网单用户
网络与身份443 统一入口；认证、角色、CSRF、上传限额和正式域名 CORS。
持久化与恢复PostgreSQL 事务与恢复验证；Redis 队列；Worker 重启后未知任务可对账。
媒体安全对象存储签名 URL、hash、生命周期；拒绝任意本地路径和 file://。
秘密管理Provider、Worker、TOS 与浏览器凭据集中存储、轮换、脱敏，不进入前端和 Agent 上下文。
运维证据结构化日志、trace_id、队列和费用告警；每日备份，每周隔离恢复演练。
发布边界交付包 ready 不等于 published；最终抖音发布必须由用户在专用 Chrome 确认。
PHASE 1 · 现在可落地

单用户稳态工作台

Windows 交互式桌面运行 FastAPI 与 Vite，SQLite/runtime 为唯一事实源，GPU Worker 通过 SSH 隧道连接。

  • 仅本机或内网访问
  • 任务计划开机恢复
  • 每日备份 + 隔离恢复
PHASE 2 · 生产化改造

持久化控制面

PostgreSQL、Redis、对象存储和持久化 Worker 上线，控制面与媒体/计算面分离。

  • 队列、租约、死信与重试
  • 签名 URL 和生命周期
  • Prometheus / Grafana / Loki
PHASE 3 · 多用户扩展

弹性与多租户

按用户、供应商、GPU 类型和预算做配额与调度，扩展多 Worker 和多区域灾备。

  • SSO / RBAC / 审计
  • 水平扩容与金丝雀发布
  • 跨节点恢复演练

07 / EVALUATION

评估方案：证据分层，结论不可替代

所有结果必须记录样本、输入版本、运行版本、费用、耗时和原始证据。NOT_RUN / BLOCKED 不计入通过率，硬失败不能靠平均分抵消。

L0 · 结构与契约

离线可重复

验证 schema、状态机、工具边界、幂等、预算、恢复和交付包结构。

  • Mock 与合成夹具隔离
  • 不声称生成真实视频
  • 失败结果保留原始证据
L1 · 真实生产

全链路可交付

在获准预算内走真实 Provider，完成真实音画、字幕、后期和 PublishPackage。

  • 至少 20 次真实任务窗口
  • 连续约 60 秒内容 5 条
  • 交付率建议 ≥ 18 / 20
L2 · 官方发布

平台事实闭环

独立验证平台账号、作品 ID、官方受理和公开状态，不以本地上传完成代替发布成功。

  • 抖音先准备后人工确认
  • 未知状态先对账
  • 未授权平台标记 BLOCKED
指标建议门槛测量方法结果状态
E02 新意≥ 4 / 5，三稿均可审冻结 10 个主题 × 3 稿，盲评并保留相似样本计划
E04 事实支持硬门槛 100%逐条 claim 对照用户资料或已核来源，无依据进入待复核计划
E07 / E08 声音音色引用 100%；CER ≤ 2%；人名术语数字 100%对照最终 TTS、朗读映射和 ASR；重合成保留版本计划
E10 身份漂移0固定人物与已审变体逐片比对，异常阻断交付计划
E14 嘴型同步中位数 ≤ 120 ms；P95 ≤ 200 ms每片至少 30 个闭唇 / 圆唇事件，报中位数、P95 和标注分歧计划
E16 字幕覆盖 100%；边界 P95 ≤ 200 ms；严重漏错 0对照批准正文与时间轴，手机尺寸检查安全区和遮挡计划
E17 / E18 媒体技术质量1080×1920、30fps CFR、H.264/AAC；−14 LUFS ± 1FFprobe、响度分析、音画时长差建议 ≤ 250 ms计划
E25 / E26 / E27 运营18 / 20 合格；5 / 5 单 GPU；成本 ≤ 授权预算真实任务批次，失败、返工、等待和 GPU 占机时间均计入未具备现状实测
当前证据边界

已有 RTX4080 Worker 与假 runner 的串行 E2E 记录：motion 约 23.2 秒、提交到终态约 126.7 秒；lipsync 约 23.2 秒、提交到终态约 217.9 秒。它们只证明阶段连通性，尚不能代表生产 P95、QPS、重启恢复或多作业排队能力。

08 / DELIVERY ROADMAP

落地顺序：先闭环事实，再扩展规模

每一阶段都有可签收的工程结果，避免先做公网入口再补数据一致性和恢复能力。

W1 · 基线冻结

补齐交付契约

统一 PublishPackage / manifest 字段、hash、父资产和质量报告；阻止 legacy 路径生成 Mock 交付包。

  • 写接口 Pydantic schema
  • 统一 Idempotency-Key
  • 契约测试与回归
W2–W3 · 可靠性

Worker 持久化与恢复

将 GPU JobStore 从进程内存迁移到持久账本，补 systemd、租约、自动重连、未知状态对账和死信处理。

  • 重启恢复演练
  • 队列 / GPU 指标
  • 不重复扣费与提交
W4–W6 · 生产化

PostgreSQL + Redis + 对象存储

完成事务、备份、PITR、签名 URL、生命周期和观察平台，再执行受控 QPS / P95 / P99 压测。

  • 一期单用户灰度
  • 压测报告入库
  • 回滚与恢复签字
W7+ · 扩展

认证、多用户与弹性

引入 SSO / RBAC、配额、租户隔离、多 GPU 调度和金丝雀发布；通过 L1 后再做 L2 平台扩展。

  • 50 QPS 控制面目标
  • 多 Worker 调度
  • 跨节点灾备演练
