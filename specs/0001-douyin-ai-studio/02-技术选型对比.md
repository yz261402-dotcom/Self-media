# 技术决策与剩余选型

版本：v2.4 · 2026-09-23。本文仅维护当前决定、未决技术及其验证依据。系统如何工作见 [总体技术方案](03-总体技术方案.md)，精确模型与渠道见 [模型接入方案](09-模型选型决策与接入方案.md)，实验顺序见 [技术验证流程](07-技术选型与实测流程.md)。

`production` 已存在真实实现；本文规定 v2.4 目标契约，角色/工具注册与内部 Worker 阻断边界已同步，真实媒体处理与生产验收仍待完成。

## 1. 当前目标与决策口径

目标是使用固定真人风格数字人和固定声音，制作抖音 AI 科普视频：**每天 5 条、每条约 60 秒**，最终交付 1080×1920 竖屏成片及发布材料。日产量是设计目标，尚无覆盖该目标的生产实测。

V1 为单用户七入口工作台，前四项完成用户逐步确认、预览和下载；后三项展示真实开发状态。排期回填、逐平台自动发布/指标、通用模型设置后续独立验收。基础配置和连接错误提示属于 V1。

决策状态与验证状态分开记录：

- `SELECTED_BY_USER`：用户已经选择，后续围绕该方案接入和验收，不重复开展全部候选竞赛。

- `PROPOSED`：建议用于下一轮试验，尚未成为正式技术决定。

- `UNSELECTED`：确有待解决的技术选择。

- `TESTED`：特定输入和版本已有真实执行证据，不等于质量通过。

- `PENDING_ACCEPTANCE`：尚有接入、质量、产能或使用条件未完成验收。

以上是文档标签，不新增业务任务状态；业务状态以 [接口契约](04-接口契约与数据字典.md) 为准。官方文档、Mock、样片可解码、用户选择和生产验收各自说明不同事实，不互相替代。

| 智能体分工 | 1 个总控 supervisor＋4 个专家 content、quality、avatar、audio | 属于当前设计；工具权限、真实并行、持久恢复与副作用去重待验证 |

| 数字人口播 MVP | **OmniHuman 1.5 音频驱动口播**：固定人物图＋已确认 MiniMax TTS＋可编辑身体/表情描述 → 有声原片 | 历史 9.48 秒样片已生成；当前人物 B、身体动作、嘴型、身份与音轨保持、分段连续及约 60 秒生产待验收；不需要另接 LivePortrait/MuseTalk |
| 可选本地口播 | M2：LivePortrait 动作底片＋已确认 MiniMax TTS → MuseTalk 1.5 | 保留已选低成本本地路线及短片实验；不能用 M2 通过替代 OmniHuman 的 MVP 验收 |

当前核心目标是固定人物随外部已选声音自然口播并产生身体运动。OmniHuman 1.5 必须在 MVP 接入和验收，不推到后续；两条路线共用人物、MiniMax 音色与最终音频，TTS 页面恢复为全部口播路线的前置步骤。声音导演合成与审核配音，数字人导演组织表演；模型输出不得擅自改正文、换声或丢弃已确认音轨。

Grok 原生有声方案已撤回当前 MVP，仅保留历史调查与 [未定稿归档](../历史版本/2026-09-23-075305-撤回Grok未定稿方案)。不再建立另一套原生声音选择流程，也不以独立视频生成替代已选音频驱动口播。

人物和声音依据见 [人物 B 与音色 3 定版记录](../selection/03-人物与音色/02-人物B与音色3定版记录.md)；M2 依据见 [口播路线定版](../../experiments/表情动作改善/EXP-001/口播路线定版.json)。选择继续有效，生产状态仍为 `PENDING_ACCEPTANCE`。

LivePortrait 迁移动作参考中的表情与运动，不直接按最终音频生成语义情绪、手势或全身动作；MuseTalk 负责依据音频生成嘴型。动作参考的质量、时长和适用权利需要独立确认。现有一台 GPU 的重型作业先串行排队，Agent 的逻辑并行不表示可以同时运行多个 GPU 推理任务。

### 2.1 专家、Skill 与 MCP 边界

| 角色/组 | 责任 | 明确不做 |
|---|---|---|
| `supervisor` | 建立任务依赖、分派专家、汇总报告、暂停/恢复和等待用户确认 | 不替 Worker 编写剪辑方案；不绕过业务门禁或代替 quality 事实确认 |
| `content` | 读取提示词、关键词、目标时长、用户资料，调用 DeepSeek 生成 3 个稿件候选；根据 quality 的有限反馈改稿 | 不联网搜索、不爬取、不调用来源抓取工具、不伪造 URL 或事实证据 |
| `quality` | 每阶段及最终成片审核；调用本地历史查重；核对用户资料、规则、媒体检测和人工复核结果 | 不把 DeepSeek 自评当成事实验证；不把无依据的最新信息标成已证实 |
| `avatar` | 人物/衣景/表演计划及 OmniHuman 或 M2 任务组织 | 不改稿、不换音色、不代替最终成片审核 |
| `audio` | MiniMax 音色试听、表达计划、TTS 合成、音频质检和用户确认 | 不让视频模型改词或换声 |
| S01-S06、S08 | 7 个业务 Skill，分别承载角色、内容、质量、音频、口播和运行规范 | 删除 S07 字幕与剪辑 Skill，不重编号 |
| M01 | 本地内容查重；仅 quality 可调用 `search_content_history` | 无 `search_sources`、`fetch_source` |
| M02 | 角色资产、声音资产与记忆读写 | 不直接改正式状态或预算 |
| M03 | 媒体生产 Provider/Worker 作业登记、查询和产物读取 | 不承载字幕、封面和交付业务决策 |
| M04 | 媒体检测与审核证据读取/登记 | 无 `align_subtitles`、`render_video` |

M05 交付 MCP 删除。字幕对齐、FFmpeg＋libass、FFprobe、清晰度增强、封面、manifest/包登记等确定性步骤由代码 Worker 在业务依赖满足后自动触发，工具名不进入 MCP 暴露面。仍保留历史内容库查重，但没有外网资料库依赖。

## 3. 剩余技术选型矩阵

优先验证一套最小工程组合，只有暴露实际缺口后再扩展候选。以下均为建议或待选，不能因写入文档而视为已实现。

| 环节 | 下一轮范围 | 必须回答的问题 | 当前状态 |
|---|---|---|---|
| Python 服务接口 | Python＋FastAPI | 模型和 DeepAgents 适配、契约校验、持久 Worker 边界是否清晰 | `PROPOSED` |
| 业务数据与检索存储 | PostgreSQL＋SQLAlchemy；需要向量检索时试验 pgvector | 任务/资产版本一致性、并发写入、迁移恢复、向量元数据过滤是否满足要求 | `PROPOSED` |
| 持久任务与定时 | 持久 Worker＋APScheduler | 重启恢复、定时重复触发、任务抢占、GPU 排队和提交结果未知时如何核对 | `PROPOSED` |
| DeepAgents 持久化 | 持久 checkpoint 与长期 Store 分开设计；后端适配和版本待验证 | 暂停后跨进程恢复、并行分支合并、资产引用一致性；长期记忆不能代替任务账本 | 主框架已选，后端 `UNSELECTED` |
| 工作台前端 | Vue 3 / React 保留候选，比较同一七入口、作品和用户选择流程 | 三稿对照、试听/预览、版本返工、进度恢复和真实占位状态是否清晰 | `UNSELECTED` |
| 本地历史查重 | 文本精确查重先行；embedding/重排模型待测 | 能否区分重复表达与新问题、新解释、新案例，是否能追溯历史稿件版本和已提供资料 | `UNSELECTED` |
| 字幕与音频检查 | 两路按已确认 MiniMax TTS 对齐；另检查最终视频音轨与该 TTS 的内容、时间及声音是否保持 | 最终音轨的术语、漏字、时间轴和逐词粒度是否可靠 | `UNSELECTED` |
| 人物、口型与声音检查 | 媒体技术规则＋人工视听基准；所需视觉、音频检测工具待测 | 如何定位身份漂移、嘴部伪影、错位、音色异常及误报 | `UNSELECTED` |
| 后处理与资产文件存储 | FFmpeg＋libass、FFprobe 和清晰度/封面/包登记由确定性 Worker 执行；文件持久化实现待定 | 编码与字幕质量、临时文件清理、不可变原件、失败恢复和可追溯性 | `PROPOSED` / `UNSELECTED` |

Skills 用于存放可复用的执行规则与领域步骤，MCP 用于接入受控外部工具，记忆层用于固定人设、任务上下文和审核后的历史经验。三者是架构能力，不是新的模型，也不会自动获得事实准确性、账号权限或跨进程持久性。具体边界见 [Agent 编排方案](10-Agent编排选型与整体架构.md)。

质量审核智能体贯穿各环节，但不能单凭文本模型自评分判定视觉、音色或口型合格。结论必须引用稿件版本、事实来源、资产哈希、音视频时间码、检测结果或人工评审记录；拒收需要返回可执行修正要求。

### 3.1 内容事实边界

content 只处理用户输入：提示词/关键词、目标时长、受众、文案类型以及用户提供的资料。若资料中没有可核对依据，涉及事实、时效、数字、案例或产品能力的内容标 `待复核`，并提示用户提供依据或人工确认；quality 可以检查内部一致性和历史重复，但不能声称模型自审已验证事实。允许复用用户提供或系统已有的已核资料，必须保存来源说明；禁止生成虚假链接、引用或 URL。

三稿都保存版本和质量报告。quality 的有限反馈最多触发配置次数的改稿，不能通过反复改写把无依据断言变成已验证事实；不足三稿时显示缺额并等待用户决定。

两服务仍为 `studio-core` 与 `studio-media`，本轮不引入新的部署服务。

## 4. 下一步怎样定版

按 [技术验证流程](07-技术选型与实测流程.md) 顺序推进：先验证 DeepAgents 模拟编排、依赖、拒收、持久恢复和提交去重；在适用预算下核验真实 DeepSeek 兼容和 OmniHuman 图＋最终音频驱动。先测试人物 B 的短片身体运动、声音保持、表情与嘴型，再做约 60 秒连续作品和每日 5 条。OmniHuman 是 MVP 必验项，M2 样片不构成替代验收。

工程组合通过相关试验后，记录版本、适用范围和已知限制，再将对应项从 `PROPOSED` / `UNSELECTED` 转为正式决定。已选模型出现问题时记录未通过及修正方案，不静默更换渠道、人物、音色或口播路线。

成本以“合格交付包”为单位，分路线记录相同的文本、人物图、TTS 和后期成本，以及各自视频生产成本。用户已确认 OmniHuman 为 1 元/生成秒（100 分/秒），当前据此估算：60 秒视频费约 60 元，每天 5 条约 300 元，30 天约 9000 元。实际账单、分段取整规则尚未核验；TTS、图像/文本、失败返工与存储另计。报价确认不等于实际调用预算授权，生成前仍须适用预算。

M2 单列 GPU 启停、推理、空闲和返工；一次性角色资产成本单列。保留两路质量、时延、合格成本对照，当前证据不足以承诺稳定单价或日产量。
