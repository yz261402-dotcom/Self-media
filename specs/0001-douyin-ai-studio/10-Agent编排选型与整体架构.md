# DeepAgents 编排、Skill、MCP 和记忆设计

版本：v2.4；日期：2026-09-23（提示词直接写稿、四类子智能体、代码后期）。**DeepAgents 主框架由用户选定；production/ 已有工程代码，本轮已同步四角色/工具白名单、7 个 Skill 和内部后期入口，真实媒体能力与全链路仍待验收。** 本文只展开 [03 总体技术方案](03-总体技术方案.md) 中的智能体协作与基础能力，不再列第二套整体架构。

[打开当前多智能体架构图](../架构图/DeepAgents多智能体架构.html) · [输入输出速查](08-端到端技术流程与模型选型地图.md)

首版七个入口围绕同一个 Work（作品）组织。人物与稿件经审核选择后，MiniMax TTS 通过质检并由用户试听确认，再进入第 4 页视频合成：OmniHuman 使用固定人物图＋最终音频＋可编辑身体/表情描述直接生成口播，M2 使用动作底片＋相同音频对口型。TTS 是两路共同前置；质量审核、用户选择和费用授权分开。Grok 退出当前 MVP，后三个后续入口展示真实开发状态。

## 1. 框架在代码里如何体现

拟以 Python `deepagents.create_deep_agent` 创建总控，通过 `subagents` 仅定义策划文案、质量审核、数字人导演、声音导演四类角色。后期由业务服务直接调度代码，不注册 editor 或其他同义后期角色。各角色显式配置职责、允许工具、Skill 与模型；不要将总控的全部权限继承给每个角色。

总控和专业角色先使用 DeepSeek 官方文本模型作为决策模型，经兼容的 LangChain 模型适配器接入；精确型号见 09。工具调用格式、多轮 tool result、错误恢复、结构化产物和并行委派必须在真实账号验证，不用普通聊天成功替代。

不开放通用浏览器、任意 HTTP 抓取或 shell 来绕过已删除工具；模型 API、受控云媒体上传/下载不属于内容搜索，继续按 Provider 白名单使用。

DeepAgents 基于 LangChain / LangGraph，底层 checkpoint、中断和 Store 能力用于执行恢复。业务层校验工作项、产物和质量结论；Agent 负责形成决策，确定性服务负责执行约束。包版本在隔离安装与兼容试验后锁定，不把示例 API 当作已锁定生产接口。

## 2. 角色配置与最小权限

| ID | 专业角色 | 允许能力 | 正式写入边界 |
|---|---|---|---|
| `supervisor` | 总控 | 委派、查进度、读取报告、提出返工/交付请求 | 经业务校验登记计划和汇总；不能改审核结论 |
| `content` | 策划文案 | 用户提示词、关键词、风格、时长与可选自供材料直接生成三稿，按审核意见改稿 | 自己的草稿空间；提交稿件新版本；不搜索或抓取网页 |
| `quality` | 质量审核 | 查内部内容历史、读用户材料及产物、调用检测器、登记问题与审核结论 | 受版本和规则校验的审核服务；不能改被审原件 |
| `avatar` | 数字人导演 | 读角色/衣景/动作库、创建候选/变体；音频确认后提交 OmniHuman 图音驱动，或 M2 底片/口型 | 派生资产登记；不能代选身份、覆盖人物或擅自增加二次口型修补 |
| `audio` | 声音导演 | 读取所选音色、编译情绪/重音/术语、MiniMax TTS 合成与检测；复核视频声音保持 | 音频、朗读映射、报告新版本；不能擅自改变已选声音或以其他音轨代替确认 TTS |

业务层从已审文件中读取资产，工具接口不接受任意文件系统路径或任意 shell。Provider 密钥留在服务端，MCP 身份认证与厂商密钥分开；外部资料作为待核内容，不得改变系统规则或工具权限。

## 3. 并行委派和结果汇合

总控将同一期任务分为显式工作项。每项有输入版本、依赖、角色、预算、Skill 版本和输出类型。可用框架的子任务委派及运行时并发能力执行独立项；是否真正并行以开始/结束事件重叠为证据，不能只看提示词里写了“并行”。

- 策划依据用户提示词直接写稿，可与人物准备并行；稿件生成后由质量角色做内部历史查重，不以网络资料采集为前置。
- 三稿分别审核、用户选稿后，声音、人物/动作准备分叉；字幕和输出样式直接读取页面配置；质量审核可分别检查已完成的产物。
- 声音合成、人物衣景/表演要求准备可并行；TTS 经过质检和用户确认后冻结真实时长，才允许提交任一路线的口播生成。
- 字幕基于已确认 TTS 对齐，可与 OmniHuman 图音驱动或 M2 口型推理并行。OmniHuman 不依赖 LivePortrait/MuseTalk；M2 底片需覆盖真实时长。业务服务触发字幕代码作业；两路后期代码均等待合格原片/字幕，并核对输出音轨与确认音频保持。
- 每个角色使用独立工作目录或命名空间；通过受控产物清单交接，不共同改同一个脚本或音频文件。

业务依赖表决定可执行范围。总控提出的提前执行请求应被工具拒绝；单 GPU 资源锁控制重型作业，Agent 并发上限与 GPU 并发上限分别配置。汇合只接受相同稿件/表演计划的有效版本，结果顺序不影响选择。

Work 保存当前采用的资产及全部候选历史；SelectionRequest/SelectionDecision 绑定版本和摘要，用户响应前用 waiting_selection。ReviewDecision 只决定质量是否合格，Agent 不能拿质量通过代替用户采用，也不能自动点击收费路线。基础配置由服务端管理，框架不接收明文密钥。

## 4. 分段表演说明与结构化交接

`PerformancePlan` 是策划、声音、数字人与后期代码的共同输入。意图层描述每段文本、情绪、重音、停顿和动作；执行层记录供应商实际支持的参数、动作素材引用和真实时间。两路都从已确认 MiniMax TTS 写真实分段时间；长片按句切分该统一音轨并保留映射。

声音导演和数字人导演可并行返回修改建议，但不同时覆写已冻结计划。业务服务以期望版本合并，冲突交给总控协调后生成新版本。改稿或 MiniMax 声音/节奏变化使对应音频、两路口播和字幕失效。仅衣景/动作变化可复用未变且获准 TTS，但必须重查新原片的声音保持、身份与同步。

交接使用 `AgentWorkItem`、`AgentResult`、`QualityDecision`、`MemoryCandidate` 等契约，字段唯一来源为 [04 接口契约](04-接口契约与数据字典.md)。响应应含产物 ID、版本/摘要、证据和实际用量；仅返回“已完成”不能算完成。模型输出先验证，失败保留原文并在预算内修正。

## 5. 首期 7 个业务 Skill

Skill 规定角色怎样完成任务；后期是固定代码流程，不加载 Skill。当前保留 S01～S06 和 S08，删除 S07「字幕与剪辑」，不重排历史编号。以下为产品运行技能的目标清单，不是 Codex 开发技能。

### 5.1 清单、负责角色与交付物

| 编号／Skill | 主要使用者 | 输入 → 工作 → 输出 | 必须拦住的问题 |
|---|---|---|---|
| S01 选题与新意 | 策划文案 | 用户提示词、受众、风格 → 直接提出不同问题/案例角度 → 三种候选切入点 | 仅换标题；编造热度和收益；自行联网搜索 |
| S02 口播写作 | 策划文案；声音/数字人读取产物 | 提示词、三种角度、时长与可选用户材料 → 写开头、解释、例子与收尾 → 三稿、标题/简介/标签、表演意图和待核断言 | 论文腔、标题正文不一致、虚构来源、表达标记污染正文 |
| S03 事实与重复审核 | 质量审核 | 三稿、内部历史、用户材料/已审知识 → 查重复、错字、逻辑、易懂性、吸引力及事实依据 → 逐稿报告 | 用模型自审冒充事实证明；无依据的时效或关键断言直接通过；查重不可用仍放行 |
| S04 固定人物与衣景 | 数字人导演；质量审核检查 | 关键词/自由描述或固定身份、衣景要求 → 创建候选或参考编辑 → 人物变体与来源链 | 换装换成另一个人；未经批准覆盖基础人物 |
| S05 动作表情匹配 | 数字人导演；质量审核检查 | 人物、表演描述、最终 TTS、路线 → 按能力/预算组织 OmniHuman 或 M2 → 口播原片 | 未确认音频就生成；承诺任意动作；静默换路线；身体/嘴部/段间异常 |
| S06 固定声音与情绪 | 声音导演；质量审核检查 | 已选稿、MiniMax 音色、表演意图 → 编译表达并合成 → 待用户确认音频、朗读映射与真实时间 | 擅自换声；错读漏读；重新配音掩盖原片声音不符 |
| S08 分阶段媒体质量验收 | 质量审核；代码读取报告 | 人物/音频/原片/成片及检测证据 → 定位问题并复核 → 阶段报告与返工目标 | 只看日志判通过；缺检测证据；把待复核当通过 |

S01/S02 无联网步骤。历史检索由 S03 调内部工具完成，查重反馈可交给策划改稿。事实核验仅使用用户材料、已有已审知识或人工证据；外部最新价格、版本、数据等没有依据时转待复核，补充材料或移除断言后重审，不编造引用。质量角色不得另开搜索旁路。

S02 的 PerformancePlan 只是意图，不预造精确字幕时间；S06 的音频经审核及用户确认后，S05 生成口播，字幕代码按同一音轨对齐。S08 的质检职责保留，字幕/剪辑执行职责不再由 Skill 承担。所有阈值统一引用 06。

移除联网搜索/抓取工具；后期、字幕和打包函数仅供内部 Worker/业务服务调用，不再暴露给 Agent。保留历史 M01～M04 编号，删除 M05，不能以更名方式保留后期工具。

| 编号／能力组 | 主要工具举例 | 使用角色 | 输出 |
|---|---|---|---|
| M01 历史内容查重 | `search_content_history` | 仅质量审核 | 内部历史稿件、主题/观点/片段命中和相似度证据；不获取外网资料 |
| M02 角色与记忆 | `get_presenter_profile`、`list_approved_assets`、`search_memory`、`propose_memory` | 各角色按作用域使用 | 人物/声音档案、已审资产、相关经验或待审候选 |
| M03 媒体生产 | `submit_image_generation`、`submit_image_edit`、`submit_tts`、`submit_avatar_video`；M2 的 `submit_motion`、`submit_lipsync` | 数字人导演、声音导演 | 生成作业及产物引用；人物、最终音轨、底片/原片与分段来源链 |

MCP 工具中删除 `search_sources`、`fetch_source`、`draft_edit_plan`、`align_subtitles`、`render_video`、`build_publish_package`。后期相关内部 Python 函数和技术能力保留，只取消 Agent 工具入口；后续平台发布单独设计 Adapter，不在当前 MCP 增加预留发布工具。

`submit_quality_report` 必须引用真实证据，业务服务复算硬门禁；缺事实/媒体依据进入待复核。`propose_memory` 只产生候选，不能覆盖固定人物或把模型推测记为事实。媒体生成仍有 `get_media_job`、`get_media_result`、`cancel_media_job`，按角色和作业归属授权；取消只按 Provider 实际能力执行，不能伪报退款。结果传引用和摘要，大媒体留在资产库。

### 6.2 两个服务与内部代码的分工

| 服务（目标名称） | 放什么 | 边界 |
|---|---|---|
| 项目管理 MCP `studio-core` | M01 内部历史；M02 角色/记忆；M04 的审核报告登记 | 不联网搜索，不运行后期，不暴露打包/发布工具 |
| 媒体任务 MCP `studio-media` | M03 图片/TTS/口播生成；M04 媒体检测及生成作业状态 | 不暴露字幕对齐、渲染、清晰度处理或打包命令 |
| 内部 Postprocess Worker（非 MCP） | 字幕 ASR/对齐、时间线合成、清晰度处理、字幕渲染、封面与编码 | 业务事件直接调度；无 Agent 身份、无 Skill、无自然语言工具决策 |

两个 MCP 共用业务作业和资产账本，按具体工具和角色授权。媒体 MCP 可调现有云 GPU Worker，不要求直接公网暴露 GPU。Provider 密钥留在受控服务环境。内部后期 Worker 与 MCP 可共享媒体函数库，但调用入口、执行身份和授权分别核验。

### 6.3 代码后期如何执行

- **字幕触发：** 最终 TTS 已审核且用户确认后，业务服务创建字幕作业，读取正文、朗读映射和音轨摘要。ASR/强制对齐实现尚待选型，允许代码调用模型；模型不自行规划流程，也不成为新 Agent。
- **合成触发：** 原片审核通过、字幕审核就绪及版本一致后，Worker 读取用户页面选项/预设，编译受 schema 校验的时间线；FFmpeg 执行分段拼接、首尾处理、音量/帧率/尺寸规范化，libass 渲染字幕，Pillow 等生成封面。
- **清晰度处理：** 默认参数化缩放、去噪和适度锐化；不承诺恢复缺失细节，不凭输出 1080P 判清晰度合格。若接超分模型，需另行测试并锁定版本与参数，当前没有已选超分模型。
- **终审与交付：** FFprobe/解码检查生成技术证据，质量角色检查实际成片。业务服务收到有效通过报告后自动打包与开放下载；打包代码复核全套门禁，无须请求任何 Agent 调 MCP。
- **失败恢复：** 每阶段持久化输入摘要、代码/配置版本、租约、状态和产物。缺依赖不开始、未知作业先核对、旧版本迟到不覆盖、仅字幕样式改变只重渲染。严重黑帧/错位先拒收，不能盲目删帧或换声音掩盖问题。

后期执行记录使用 04 的 `StageExecution`，`executor_kind=worker`、`worker_kind=postprocess`；Agent 执行才填写 `agent_role`。后期结果写媒体/阶段记录，不伪装 `AgentResult`。代码流程由内部事件和作业状态推进，总控只读进度/报告，不接回字幕和剪辑步骤。

### 6.4 建设与迁移顺序

1. 对照已有实现，先回归角色/权限：只注册四个子 Agent；删除内容联网工具、editor、S07、M05 及后期 MCP 入口，未知旧角色/工具拒绝新任务。历史记录保留，不重写历史成功结论。
2. 验证提示词直接三稿 → 质量内部查重/表达审核 → 用户选择；重点测试缺依据时待复核，不把全局禁网误做成禁用 DeepSeek/MiniMax 等合法模型 API。
3. 保留两路数字人和固定 TTS 门禁；人物、音频、动作和原片按 S04/S05/S06/S08 验证，不以删除后期 Agent 改变口播模型职责。
4. 接内部字幕/渲染/清晰度代码、最终审核和自动打包；验证媒体实际输出、可恢复性、依赖失效和下载，不以无 LLM 调用日志代替成片验收。
5. 继续验证持久记忆审核与隔离、约 60 秒交付、每天 5 条、合格成本；平台能力后续独立实现。

本节细化 05 的 T00～T12，不新增阶段编号；验收统一引用 06。本轮不调用付费模型、不删除历史实验；现有 production/ 仅完成角色/工具边界和内部 Worker 的最小接管，真实 ASR、渲染、清晰度与合格打包仍待实现。

### 6.5 OmniHuman 的工具边界

`submit_avatar_video` 读取固定人物图、已审已确认 MiniMax TTS 和可编辑身体/表情描述，映射到 OmniHuman 1.5。输入版本、用户选择和预算有效才提交。无需 LivePortrait 或额外 MuseTalk，不能静默添加修补；M2 仍单独使用 LivePortrait→MuseTalk。

历史接口约束为音频少于 60 秒，建议不超过 15 秒，正式调用核对当期限制；长片按同一最终音轨句界切分并保存统一映射。身体运动、人物 B、嘴型和长片质量仍待验。历史 9.48 秒短片的音轨保持证据不能替代新任务审核，具体模型事实见 09。

## 7. 记忆的存储和生命周期

| 类别 | 保存什么 | 拟采用的机制 | 谁能修改 |
|---|---|---|---|
| 任务状态 | 当前对话、计划、委派、等待与检查点 | 持久 checkpointer＋业务任务表 | 当前执行，经版本/租约校验 |
| 固定人设与声音 | 角色身份、共用 MiniMax voice_id/风格、已确认音频和批准资产版本 | 不可变资产库＋版本化配置 | 用户定版流程；Agent 只读 |
| 内容历史 | 稿件、主题、观点、例子、来源、发布信息 | 业务数据库＋全文/向量检索 | 内容登记服务，保留旧版本 |
| 长期经验 | 术语读法、审稿修正、偏好、真实效果和适用条件 | 持久 Store＋经审核记忆记录 | 子 Agent 提候选，审核后由业务服务提交 |

DeepAgents 的 `StateBackend` 可作为任务工作空间；`CompositeBackend` 将指定长期路径路由到 `StoreBackend`。实际 Store 必须落到持久后端。官方示例中的 `InMemoryStore`、`MemorySaver` 不能作为跨进程恢复证明。

建议首轮评估 PostgreSQL 承担业务记录与持久运行存储，按接口区分 checkpoint、Store 和业务表；pgvector 只解决向量索引，不等于记忆治理。模型/维度变化需重建或版本化索引，不能混合检索后当同一分数。

每条经验包含来源、所属账号/角色、发生时间、适用范围、版本与复核/失效条件。任务暂存和长期内容隔离，检索仅返回相关少量记录；不存在已取得的播放数据时明确为空。并发候选使用独立 ID，合并依靠事务/期望版本，冲突不以最后写入覆盖处理。

## 8. 可恢复性与质量执行

- checkpointer 保存运行状态，业务库保存作业事实，媒体库保存文件；恢复先核对三者。
- 子 Agent 中断可交由框架人工恢复机制处理，但恢复可能重新进入工具/节点，外部副作用仍要幂等和核对。
- 质量决定绑定资产、稿件、计划与规则版本。结果 `review` 或 `not_run` 不能当 `pass`，总控不具备覆盖硬失败的接口。
- 人工改稿后创建新版本并传播失效；并行旧任务迟到的产物保留证据，不登记为当前有效输出。
- OmniHuman 按用户确认 1 元/生成秒估算：60 秒 60 元、5 条/日 300 元、30 天 9000 元，仅视频费；账单/取整未验，TTS、失败返工和存储另计。报价不是调用授权，选择和适用预算有效后提交；失败不能自动换模型或加 MuseTalk 修补。
- 单条/每日预算共享原子预留。重写次数、Agent 调用步数、并发数和媒体返工分别设限，避免子 Agent 自主循环造成不可控开销。
- GPU 队列保存提交状态和远端 ID；未知结果进入核对，实例中断不触发盲目重交。取消后仍核对已受理任务的账单。

## 9. 首轮框架试验应证明什么

本版迁移先验证四类子 Agent 和工具白名单，联网搜索/抓取及后期工具调用必须被拒绝；后期无 LLM 委派仍能按事件执行。再使用可控模拟模型和工具验证：七入口状态、用户选择/审批分离、刷新后待选恢复、付费路线选择、角色分派、独立任务重叠执行、依赖汇合、结构错误拒收、质量失败退回、返工次数和预算边界、跨进程恢复、提交成功回执丢失不重交、记忆并发冲突、改稿后的下游失效。

再在有预算的前提下验证真实 DeepSeek 的 tool calling、多轮上下文、中文结构输出与子 Agent 协作，然后接真实 Provider。模拟测试、模型兼容、视频质量、运营效果分别验收，不能互相替代。正式测试编号与测法见 [06 验收方案](06-验收标准与测试方案.md)。

### 9.1 Skill、MCP 和记忆如何评估

评估方法、公式、样本与门槛统一见 [06指标总表](06-验收标准与测试方案.md#42-指标总表)，不由每个Skill另设通过分。

- S01/S02/S03：内容事实、查重、新意、开头与口语；S04/S05：身份、动作、口型与自然度；S06：发音、音色与情绪；内部代码：字幕/编码/响度；S08：各阶段媒体质量及漏放/误拒/待复核。具体指标都在同一张总表中。
- 所有Agent与Skill：首次结构、工具决策、角色任务成功、返工上限和真实并行。Skill A/B固定主模型、工具和输入，比较质量、成功率及 tokens/费用，不只看最终输出是否存在。
- 四组能力和两个 MCP 服务：权限、副作用去重、未知受理恢复或安全阻断、结果完整性；实际生成质量仍按媒体指标另验。
- 记忆层：有效记忆 Recall@5、无答案错误召回、作用域/时效、候选审核写入与冲突保护。持久检查点另以真实重启恢复验证。
- 系统交付：20 次合格率、日产 5 条、端到端时延、合格成本与真实发布状态。模拟成绩与真实成绩分开报告。

新增阈值是待冻结的建议，不是已经测得的成绩。评估报告同时列硬门槛、感知质量、工程恢复和成本，缺证据不能靠平均分放行。
