# MuseTalk 云端部署配置与试验方案

版本：v0.1 Proposal · 2026-09-21。状态：**DOCUMENTED / NOT_RUN / UNSELECTED**。

**后续执行更新**：用户已租用实例，MuseTalk 1.5 已部署并完成四项短样片，实际为实例报告的 RTX 4080 / 32GB、1.58 元/小时。见 [部署与首测结果](04-MuseTalk部署与首测结果.md)。下文保留部署前的原方案和推荐配置，不作为当前运行状态；生产选型仍未确定。

用户因长期 API 成本考虑自托管 MuseTalk，并确认目前没有租用 GPU，先确定配置与试验方案。
本方案将下一步改为 MuseTalk 验证；已有 API 试验与失败证据继续保留。尚未租机、安装模型或执行 GPU 推理。

## 1. 推荐路线及能力边界

建议先用**单卡 RTX 4090 24GB、按量租用、MuseTalk 1.5 官方实现**完成一个受控试验。
长期部署方式优先评估“本机管理任务和资产，算力云运行生成任务，批量完成后关机”。
这是待验证的部署建议，不是生产技术栈定版。

MuseTalk 主要是音频驱动的唇形重绘。官方说明其处理脸部区域为 **256×256**，支持图片和视频输入；
视频的头部、身体与眨眼动作主要来自源素材，不能把单图输入直接等同于完整自然数字人。[M1]
1080×1920 输出画布也不表示嘴部具有原生 1080P 细节。

因此分开比较三条路线：

| 路线 | 能回答的问题 | 缺口及适用定位 |
|---|---|---|
| 单张 Base Avatar + TTS → MuseTalk | 唇形、嘴部细节、身份变化、设备成本 | 单图不提供自然头动/眨眼，主要作为唇形基线；不能直接通过完整主播验收 |
| 固定身份动作母版 + TTS → MuseTalk | 复用自然动作，重复合成不同口播，摊薄预处理成本 | 需要同身份母版，母版来源/成本/循环接缝独立验收；这是建议优先验证的组合 |
| 音频或真实动作参考驱动全脸模型，再接 MuseTalk | 在禁止 T2V 的前提下补足动作生成 | 多一个模型、额外显存/时间与身份风险；只有母版路线不合格才另立实验 |

动作母版只能来自本项目同一人物、经授权且符合原始要求的方式，例如图片＋音频驱动或动作参考驱动。
不使用文生视频，不以静态头像循环、几何嘴型或后期摆动整张图补齐动作要求。
MuseTalk 无需为每位人物重新训练；官方预处理缓存与训练/微调是不同步骤。[M1]

## 2. 租机配置：先买什么规格

| 项目 | 首测建议 | 理由与边界 |
|---|---|---|
| 平台 | AutoDL 可作第一候选；同类支持 SSH 和持久存储的平台亦可 | 已核验其官方计费/环境文档；尚未替用户选账号、地域或购买 |
| GPU | **1 × RTX 4090，24GB 显存** | 给初次依赖验证、预处理和 batch 留余量；不是官方最低要求，也没有本项目速度保证 |
| 成本对照 GPU | RTX 3090 24GB | 完成一次稳定基线后再比较实际每条合格片成本；低小时价不一定更便宜 |
| CPU / 内存 | 约 8 vCPU / 至少 32GB RAM，64GB 更利于缓存较长母版 | 是资源规划建议；长帧序列占用主存，不能只看显存 |
| 系统 | Ubuntu 22.04 容器或兼容 Linux 镜像 | 首测统一 Linux，避免将本机 Windows 依赖问题混入 GPU 选型 |
| 数据盘 | 至少 50GB 可用；预留到约 100GB 容量时先核实扩容价格 | 保存权重、环境、帧缓存和原片；不是宣称模型固定占用 100GB |
| 接入 | SSH / SFTP，先 CLI 离线任务 | 单人批量试验无需先建设公网 Web 服务、队列或生产 API |
| 计费 | 按量、首测单卡、用完确认实例关机 | 不租月卡，不用 24 小时常驻方式推断“自托管更省钱” |

首测选 4090 的目的是尽快取得稳定质量与时间基线；之后若 3090 在相同质量门槛下单位合格片成本更低，再调整。
不先租 A100/H100，也不把 README 中 4GB 能运行的案例当作生产推荐。
官方有 Windows 3050 Ti 4GB / fp16 / 8 秒约 5 分钟的声明，以及 V100 30 fps+ 的另一套声明；
环境与测量范围不同，不能外推为本项目 4090 整条视频实时完成。[M1]

### 2.1 环境版本与安装前检查

官方 README 建议 Python 3.10，给出的 PyTorch 安装组合为 torch 2.0.1、torchvision 0.15.2、
torchaudio 2.0.2 和 cu118；MMLab 示例为 mmcv 2.0.1、mmdet 3.1.0、mmpose 1.1.0。[M1]
README 同时出现 CUDA 11.7 环境建议和 CUDA 11.8 安装命令，应以实际锁定的 cu118 依赖组合核验，
不能混装，也不能把 `nvidia-smi` 显示的驱动支持版本当作 Python 已安装的 CUDA 运行时。

租机前保存镜像标识、系统版本、GPU 型号、实际显存、CPU/RAM、数据盘和单价。
部署时记录代码 commit、权重来源/文件哈希、依赖锁定结果、CUDA 可用性和一次最小推理结果。
先使用独立环境，不升级或覆盖用户其他环境；编译 mmcv 等扩展前核对匹配的二进制轮子。

AutoDL 官方明确：普通容器实例内部不支持再使用 Docker，不能预设在其中运行 Docker Compose。[C2]
因此该平台首测在租用的容器中使用独立 Conda 环境；若选择能运行 Docker 的其他实例，再单独锁定镜像。

## 3. 本机与算力云的责任

```text
本机：角色资产、最终 TTS、任务清单、预算、结果评审、历史证据
  ↓ 上传已冻结输入与任务清单（SHA-256）
算力云：输入核验 → 母版预处理/缓存 → MuseTalk → 原片与运行记录
  ↓ 下载原片、耗时/资源记录，校验哈希
本机：原片质检 → 再决定字幕/规格转换 → 保存运行报告
  ↓ 确认结果落地和远端无任务后
算力云：关机并核对计费状态
```

未来接入统一 Provider 时，可用自托管 Adapter 替换模型调用层，业务管线仍只消费任务与资产。
首测先运行官方 CLI，验证效果后再设计并实现 submit/status/result/cancel 契约；
不把未存在的 HTTP 服务、恢复能力或定时开关机接口写成已实现。

缓存至少绑定：Base Avatar 版本、服装/背景/动作母版版本、素材哈希、MuseTalk/权重版本、
人脸框/遮罩/裁剪参数、帧率与精度。更换衣服或背景不能复用旧画面缓存；缓存本身也不能解决人物一致性。
模型环境可做镜像，数据盘中的权重/母版/缓存还需要独立保留；AutoDL 数据盘不随系统镜像保存。[C2]

## 4. 首次试验：先用现有新项目素材

实验编号建议 `MT-001`，结果另建目录，不覆盖 `TH-AB-001` 的原图、WAV、账本或 MP4。
当前仅有下面第一组独立同图同音频比较素材；其他测试在此基础上明确标注输入变化。

### 4.1 输入与版本冻结

- 图片：测试人物.png（原件未随仓库分发），1080×1920。
- 音频：测试口播.wav（原件未随仓库分发），真实 9.36 秒，24 kHz / 单声道。
- 输入哈希与来源：首轮输入清单（原件未随仓库分发）。
- 独立参照：阿里原片（原件未随仓库分发），仍未通过主观完整视听。
- 官方代码：MuseTalk 1.5，锁定核验文件中列出的 commit 和实际下载权重 SHA-256，不跟随 main 自动更新。

WAV 已知存在声明长度与实际采样长度不符的问题。首次优先使用原文件；
如解析器不接受，允许另存正确 WAV 封装，但必须验证解码后 224,640 个 PCM 采样逐字节相同，
记录原文件与派生文件两个摘要，不能顺便裁剪/加速/补静音，并在对比报告注明封装差异。

官方推荐 25 fps 源视频，首测记录原生输出 25 fps 与 256×256 脸部处理事实。
与阿里 30 fps 原片比较时统一显示尺度并注明帧率差异；不以提前补帧/锐化得到的流畅度和清晰度给模型加分。[M1]
M2～M4 的源片是 30 fps，应先用 FFmpeg 另存保持时长、以丢帧/重复帧采样到 25 fps 的派生母版，记录命令与新哈希；
不覆盖阿里原片，不做生成式补帧。官方 realtime 逐帧读取源片，单改 `--fps 25` 不会按时间戳重采样 30 fps 素材，反而会改变动作速度。

### 4.2 首轮四个受控任务

| 顺序 | 输入与模式 | 目的与限制 |
|---|---|---|
| M1 单图基线 | 新项目原图 + 原 9.36 秒 TTS；normal，fp16，单次 | 与阿里同图同音频参照；验证唇形/身份/画质和资源，不能用此证明自然头动 |
| M2 母版预处理 | 现有阿里原片作为**临时动作母版** + 原 TTS；官方缓存流程，单次 | 验证视频输入与预处理；动作、部分画质来自阿里，属于组合诊断，不属于独立 MuseTalk 对照 |
| M3 缓存复用 | 同一母版和参数 + 原 TTS；同一已加载进程中复用缓存，单次 | 记录排除准备阶段后的增量生成时间；如果实际重新加载了模型，标记为含启动耗时 |
| M4 音频变化诊断 | 同一母版 + 将原 TTS 延后 0.5 秒的诊断音频，单次 | 检查嘴部是否随新音频变化，防止把原母版嘴型当作生成能力；诊断 WAV 不用于发布或主质量排名 |

M4 的派生音频只在开头补 0.5 秒静音、保留完整原 PCM，总长 9.86 秒，记录构造方法和哈希。
它与原音频任务不是同输入画质对比。要检查开头静音时的嘴型，以及后续音素是否随延迟移动，
不能把波形相关当作口型验收。

M2～M4 只有在 M1 可解码且没有严重身份/嘴部破坏后继续。
现有阿里片仅约 9.13 秒，而且是同一口播内容；同音频再跑不能独自证明重新驱动能力，因此有 M4。
母版沿用阿里结果，也意味着存在一次性云生成成本，必须计入资产成本；不能宣称整个组合完全无 API 来源。
首测结果若提示源片瑕疵或重复动作不适用，应停止该母版路线，不能循环播放这段视频冒充合格长片。

任务采用本项目建议的显式 `--batch_size 4` 起步；官方 normal 默认 8、realtime 默认 20，4 不是官方默认或最低要求。记录实际精度、batch、bbox 和遮罩配置。
不以 batch 越大越好。OOM 或失败保留当次记录，首次试验不自动换精度、调参数重跑，先诊断再登记后续任务。
官方 realtime 的 avatar 目录没有完全跟随 `--result_dir`，因此使用独立工作目录与版本化 avatar ID，核查实际落盘位置，禁止覆盖旧缓存。
普通推理单图分支还存在清理变量的静态疑点，首测分别记录进程退出、日志与原片状态，不仅凭“有 MP4”判流程成功；若复现，先离线测试修复再安排下一次推理。

### 4.3 测量项目与通过条件

每个任务记录完整墙钟时间，拆分权重下载/安装、进程加载、母版准备、推理、合成编码与传输；
同时记录开机计费时间、GPU 利用率/峰值显存、进程内存峰值和缓存/原片体积。
推理 fps、仅网络前向 fps、端到端耗时分别报告，下载和安装不能隐去。

质量检查沿用 [选型门槛](../../0001-douyin-ai-studio/07-技术选型与实测流程.md)：
全片与基准图对照；“妈妈/爸爸/白茶”等音素的闭唇/张口/停顿；牙齿、唇缘、矩形融合边界、下巴和肤色；
头动/眨眼是否自然，声音及首尾字是否保持。任何严重身份变化或语音缺失都不以低成本抵消。
M1 可以通过唇形子项而未通过完整主播；M2～M4 也只证明其组合范围，不归功于 MuseTalk 单模型。

至少保存原片、统一尺寸对照截图、完整视听记录及具体问题时间点。
先取得本轮短片质量结论，再做真实不同内容的 60～75 秒音频、动作循环接缝与多个服装/背景的后续试验。
后续长音频必须实际包含完整独立口播，不把 9 秒语音重复七次当内容生产验收。
本轮没有足够样本统计可靠成功率或 P95，也不能直接将 MuseTalk 改成 SELECTED。

## 5. 预算建议与长期成本口径

**新 GPU 试验建议封顶 30 元、最多开机 3 小时，先到者停止。** 这是待批准的预算建议，尚未执行；
旧 60 元授权针对已完成的固定 API 次数，不覆盖新租赁。租赁前需要平台实时报价和该轮额度。
预留备份与关机时间，使用平台能实际执行的超时关机措施；停止 Python 进程不等于停止租机计费。[C1]
当前阶段先提供可审阅配置与方案，不申请租机、不扩容或创建收费资源。

选实例时要求 `3 × 实际小时价 + 预计存储/传输及其他费用 ≤ 30 元`；
若实际报价不满足，先缩小批准的时长或换配置，不能越过上限。
安装/下载占用租赁时间也算入本轮，不能默认免费；环境问题消耗时长时停止无效等待。

每条合格片的真实费用计算：

```text
云端本轮费用 = 小时单价 × 实际开机小时 + 磁盘/镜像/传输费用
单位合格片成本 = (本轮费用 + 动作母版与一次性准备成本的合理分摊) / 合格片数量
项目总成本 = 上述费用 + TTS + 内容/质检模型 + 后处理 + 运维人力
```

失败、参数诊断、空闲等待和重新加载都计入开机成本；合格片数量为 0 时报告“无合格产出”，不除以零或伪填低单价。
本轮算出的单位成本仅供该短样本参考，长片需要另测。

阿里已核验的 720P 标价是 0.9 元/视频秒，按此单纯外推，60 秒为 54 元，75 秒为 67.5 元；
它们只是视频秒数计价算例，S2V 仍需按接口时长限制分段，也未包含全部生产成本与优惠。

下面仅是计费敏感性算例，**2 元/小时不是当前市场报价**：

| 假设使用方式 | 仅计算 GPU 开机费用 | 说明 |
|---|---|---|
| 一个月实际开机 10 小时 | 2 × 10 = 20 元 | 不能由此保证能生成多少合格视频 |
| 一个月每天开机 1 小时 | 2 × 30 = 60 元 | 还要加存储、启动和素材成本 |
| 连续开机 30 天 | 2 × 24 × 30 = 1,440 元 | 对低产量可能浪费明显，需与实际产量比较 |

选 3090 或 4090 要比较实际 `小时价 × 完整任务耗时 / 合格产出`，而非只看型号或小时单价。
AutoDL 明确按开关机计费，关机后付费扩容盘仍可计费；再次开机可能没有空闲同型号 GPU。[C1]

## 6. 决策规则与下一步交付

本阶段已确定的是**先验证自托管以控制长期成本的方向**；未确定的是模型质量、平台/实例、长期成本和生产依赖。
不再把修好火山权限或补齐两家 API 样片作为 MuseTalk 试验前置条件。

租机前完成：选定实际平台和单卡报价、确认 3 小时/30 元建议是否可行、锁定模型与依赖许可、准备输入清单。
GPU 试验后交付：真实原片、运行环境与资源曲线、费用记录、质量问题时间点，以及“淘汰/保留唇形模块/继续母版组合验证”的结论。
只有目标长片、同身份变体、质量、恢复与成本覆盖后，才将限定范围的自托管组合写入正式技术方案。
