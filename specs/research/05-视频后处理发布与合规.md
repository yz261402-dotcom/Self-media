## 0. 结论速览

| 编号 | 决策点 | 推荐 | 理由 | 置信度 |
|---|---|---|---|---|
| V1 | 后处理执行引擎 | ffmpeg 单链路 + 两遍 loudnorm | 全部需求（帧率/同步/响度/锐化/降噪/封装）ffmpeg 原生覆盖，无外部依赖 | 高 |
| V2 | 后处理顺序 | 探测 → 去首尾 → 规格统一+增强 → 响度 → 封装 | 剪裁会改变时间轴，必须先做；loudnorm 必须最后做（两遍法第二遍需完整音频） | 高 |
| V3 | 音频响度目标 | `I=-14 TP=-1.5 LRA=11` | 抖音等移动端 UGC 平台普遍以 -14 LUFS 为归一目标（EBU R128 电视标准为 -23，对短视频过轻） | 中 |
| V4 | 编码参数 | libx264 `-preset slow -crf 20 -profile:v high -pix_fmt yuv420p`，音频 AAC 192k/48k | 兼顾画质与体积；`-pix_fmt yuv420p` 是抖音播放兼容硬要求 | 高 |
| V5 | 清晰度增强 | **纯 ffmpeg 链**（lanczos + hqdn3d + unsharp），**不上 Real-ESRGAN/GFPGAN/CodeFormer** | 云 API 数字人输出本身已是 720p/1080p 干净源，超分收益极低；4GB 显存跑 GFPGAN/CodeFormer 不现实（见 §2） | 中高 |
| V6 | 字幕时间戳来源 | 优先 TTS 直出词级时间戳；**必须实现 ASR 回退** | 云 TTS 是否返回时间戳因厂商而异，不能作为唯一路径（见 §3.3） | 中 |
| V7 | 字幕样式 | 单行 ≤ 14 字、最多 2 行、底部安全区上方 `margin_bottom` 320px@1080×1920、描边 3~4px | 与你现有 config 一致，仅需微调 | 中高 |
| V8 | 封面自动化 | 抽帧 + PIL 合成标题（你现有 `_make_card` 思路可复用），尺寸 1080×1920 | 抖音封面随视频竖屏比例，无需单独设计器 | 中 |
| V9 | **抖音官方 API 能否支撑全自动发布** | **不能。必须放弃"无人值守全自动发布"的幻想** | 官方发布能力是「拉起抖音 App + 用户手动点发布」的 SDK/H5 投稿，**没有服务端直接投递接口**（见 §5、§6） | **高** |
| V10 | config 中 `upload_url` | **当前值是错的，必须改** | `https://open.douyin.com/video/upload/video/` 实测 **404 Unsupported path(Janus)**（见 §5.2） | **高** |
| V11 | config 中 `create_url` | 路径存在但**不构成发布能力** | `/video/create/` 实测返回 200 + `access_token无效`，说明路由存在；但无权调用且属历史路由（见 §5.2） | 高 |
| V12 | 替代发布路径 | **本地发布就绪包 + 人工确认**（你现有 `drafts.py` 方向正确），可选合规第三方 SaaS | 网页自动化属高风险违约行为，不予推荐（见 §7） | 高 |
| V13 | Adapter 设计 | 保留现有分层，增加 `capability` 探测 + 幂等键 + 状态回写 | 见 §8 | 高 |
| V14 | AI 生成内容标识 | **必须加显式标识 + 元数据隐式标识**，这是法定要求 | 主播为全 AI 虚拟人，触发标识义务（见 §9.1，法规名称需复核） | 中（法规细节待核验） |

**本次调研最重要的三条结论：**

1. **抖音开放平台的"发布内容至抖音"不是服务端 API，而是 SDK/H5 投稿能力** —— 从你的 App/网页拉起抖音 App，内容填入抖音的编辑页，**由用户手动点发布**。`[文档实测]` 原文：「从App拉起抖音App，投稿内容直接传入内容编辑页/发布页」「用户可手动添加/修改参数，**手动操作发布**」。这直接否定了"AI 系统全自动发抖音"的技术可行性。
2. **资质门槛极高，个人开发者拿不到** —— `[文档实测]`：应用主体「不再向个体工商户类型主体开放；若主体类型为企业，需满足注册资本≥50万且注册时间≥1年」；应用类型「仅对**创作工具、社区、硬件配套、游戏**类应用开放，其他类型应用暂不支持」；使用场景「如涉及**企业宣传、商品介绍、诱导分享等营销类内容分享，将不开放该能力准入**」。
3. **"代发"在规范层面被明确限制到几乎不可用** —— `[文档实测]`《移动/网站应用能力申请及使用规范》：「开发者在使用代替用户发布内容到抖音的相关能力时，**仅可用于企业内部或者签约的账号的内容管理**。同时，实时发布或者预设发布**需要用户自己在第三方应用上进行操作**，且需明确告知用户将内容同步到哪个抖音上…并支持用户勾选「是否同步」、「是否删除」」。同时「不得大量发布同质化内容，包括但不限于：**同个账号多次发布相似视频、相似视频发布到多个账号上**」——这一条对 AI 批量生成矩阵账号是致命的。

## 1. 后处理标准链路（可直接拷贝的 ffmpeg 命令）

### 1.0 参数基线

| 项目 | 取值 | 说明 |
|---|---|---|
| 分辨率 | 1080×1920 | 9:16 竖屏 |
| 帧率 | 30 fps CFR | 恒定帧率，禁用 VFR |
| 视频编码 | libx264 / H.264 **High** profile / level 4.1 | 兼容性最佳 |
| CRF | 20（成品）/ 18（中间态） | 你的 config 用 18 偏重，成品建议 20 |
| 目标码率 | 6~8 Mbps（1080p 竖屏） | 抖音推荐 4~8 Mbps，别超太多 |
| preset | slow（成品）/ medium（中间态） | slow 体积收益明显 |
| GOP | keyint=60, min-keyint=30 | 2 秒一个关键帧，利于拖动与平台切条 |
| 像素格式 | yuv420p | **硬要求**，否则抖音可能黑屏 |
| 音频 | AAC-LC / 192k / 48kHz / 2ch | 48kHz 优于 44.1kHz |
| 响度 | I=-14 LUFS, TP=-1.5 dBTP, LRA=11 | 两遍法 |
| 容器优化 | `-movflags +faststart` | moov 前置，秒开 |

### 1.1 探测源文件

```bash
ffprobe -v error -of json \
  -show_entries stream=index,codec_type,codec_name,width,height,r_frame_rate,avg_frame_rate,sample_rate,channels,nb_frames \
  -show_entries format=duration,bit_rate,size \
  input.mp4
```

### 1.2 检测黑帧与静音（用于首尾裁剪）

```bash
# 黑帧检测（阈值 0.10，持续 ≥0.1s）
ffmpeg -hide_banner -i input.mp4 -vf "blackdetect=d=0.1:pix_th=0.10" -an -f null - 2>&1 \
  | grep -E "black_start|black_end|black_duration"

# 静音检测（-35dB，持续 ≥0.6s）
ffmpeg -hide_banner -i input.mp4 -af "silencedetect=noise=-35dB:d=0.6" -vn -f null - 2>&1 \
  | grep -E "silence_start|silence_end|silence_duration"
```

> 注意：`-35dB` 比常见默认 `-50dB` 更激进，更适合数字人无环境底噪的干净音频；但若背景音乐较强，需放宽到 `-45dB`。你现有 config 的 `silence_noise_db` 建议设 `-35`、`silence_min_duration` 设 `0.6`。

### 1.3 主增强链（规格统一 + 降噪 + 锐化 + 调色）

```bash
ffmpeg -y -hide_banner -i trimmed.mp4 \
  -vf "fps=30,scale=1080:1920:flags=lanczos+accurate_rnd+full_chroma_int,\
hqdn3d=1.5:1.2:4:4,\
unsharp=5:5:0.55:5:5:0.0,\
eq=contrast=1.03:saturation=1.06:gamma=1.0,\
format=yuv420p" \
  -r 30 -vsync cfr \
  -c:v libx264 -preset slow -crf 20 -profile:v high -level 4.1 \
  -x264-params "keyint=60:min-keyint=30:scenecut=1:bframes=3:ref=3:rc-lookahead=40" \
  -maxrate 8M -bufsize 16M \
  -af "loudnorm=I=-14:TP=-1.5:LRA=11:print_format=summary,\
aresample=async=1:first_pts=0:resampler=soxr" \
  -c:a aac -b:a 192k -ar 48000 -ac 2 \
  -movflags +faststart -shortest \
  main.mp4
```

**参数裁决与坑：**

| 参数 | 建议值 | 为什么 |
|---|---|---|
| `scale` flags | `lanczos+accurate_rnd+full_chroma_int` | 后两个 flag 提升色彩精度，几乎零成本，你现有代码只用了 `lanczos` |
| `hqdn3d` | `1.5:1.2:4:4` | 你现有 config 值，合理。数字人视频噪点少，**不要超过 2.0**，否则皮肤塑料感 |
| `unsharp` | `5:5:0.55:5:5:0.0` | 亮度锐化 0.55，色度不锐化（第 6 位 0.0）。**不要超 0.8**，否则边缘出现白边光晕 |
| `eq` contrast/saturation | `1.03` / `1.06` | 轻微提升即可。**饱和度过 1.15 会溢出，抖音二次压缩后出现色块** |
| `-vsync cfr` | 必须 | 与 `fps=30` 配合确保 CFR；VFR 会导致音画不同步累积 |
| `aresample=async=1:first_pts=0` | 必须 | 强制音频从 0 起，修正时间基偏移 |
| `-shortest` | 建议 | 防止音视频轨长度不一致产生尾部静帧 |

### 1.4 loudnorm 两遍法（推荐，精度高于单遍）

单遍 loudnorm 是动态模式，音量会随时间浮动，对**带 BGM 的口播**尤其明显。两遍法先测量再静态归一：

```bash
# 第一遍：仅测量
ffmpeg -hide_banner -i main.mp4 -af "loudnorm=I=-14:TP=-1.5:LRA=11:print_format=json" \
  -f null - 2>&1 | tail -n 20
```

输出形如（示例结构，实际数值以你的文件为准）：

```json
{"input_i":"-19.83","input_tp":"-2.11","input_lra":"6.20","input_thresh":"-30.05",
 "target_offset":"0.32"}
```

```bash
# 第二遍：套用实测值，linear=true 静态归一
ffmpeg -y -hide_banner -i main.mp4 \
  -af "loudnorm=I=-14:TP=-1.5:LRA=11:measured_I=-19.83:measured_TP=-2.11:measured_LRA=6.20:\
measured_thresh=-30.05:offset=0.32:linear=true:print_format=summary" \
  -c:v copy -c:a aac -b:a 192k -ar 48000 -ac 2 -movflags +faststart \
  normalized.mp4
```

> 关键坑：第二遍 `-c:v copy` 可避免二次编码画质损失。若 `linear=true` 报错（测量值与目标差距过大），退化为省略 `linear` 的动态模式。

### 1.5 首尾裁剪（裁剪 + 重编码 + 时间基准归零）

```bash
ffmpeg -y -hide_banner -ss 0.35 -to 42.80 -i input.mp4 \
  -c:v libx264 -preset slow -crf 20 -profile:v high -pix_fmt yuv420p \
  -c:a aac -b:a 192k -ar 48000 \
  -avoid_negative_ts make_zero -movflags +faststart \
  trimmed.mp4
```

> `-ss` 放在 `-i` **之前**是快速定位（关键帧级），精度可能不足；若需帧级精确，把 `-ss` 放到 `-i` **之后**并用 `-accurate_seek`。首尾裁剪场景建议 `-i` 之后以保证精度。

### 1.6 片头片尾拼接

```bash
# list.txt（每行一个文件，路径用正斜杠）
printf "file 'intro.mp4'\nfile 'main.mp4'\nfile 'outro.mp4'\n" > list.txt

ffmpeg -y -hide_banner -f concat -safe 0 -i list.txt \
  -c:v libx264 -preset slow -crf 20 -profile:v high -pix_fmt yuv420p \
  -r 30 -vsync cfr \
  -c:a aac -b:a 192k -ar 48000 -ac 2 \
  -movflags +faststart final.mp4
```

> **你现有 `composer.py`/`postprocess.py` 的坑**：concat demuxer 要求所有片段**编码参数完全一致**（分辨率、像素格式、帧率、时间基）。你的 `_make_card` 生成的静态卡片若与主体帧率/时间基不同，会出现拼接处音画错位。建议拼接前统一走一次 §1.3 的同一套参数重编码。

### 1.7 对你现有实现的真实度评估

| 模块 | 现状 | 评价 | 修正建议 |
|---|---|---|---|
| `composer.py` 逐帧渲染 + 1080×1920 H.264/AAC | 方向正确 | 逐帧渲染性能差，30fps×60s=1800 帧 | 改用 ffmpeg 原生滤镜链（如 §1.3），比逐帧快 1~2 个数量级 |
| `enhance.py` Lanczos + 降噪 + 锐化 + 调色 | 参数合理 | 与你 config 值一致，可用 | 补 `accurate_rnd+full_chroma_int`；`realesrgan` 分支见 §2 |
| `postprocess.py` 帧率统一/音画同步/loudnorm/去黑帧/首尾 | 流程完整 | **单遍 loudnorm**，精度不足 | 改两遍法；`-vsync cfr` 已在，正确 |
| `_detect()` 用 stderr 正则抓检测结果 | 可行但脆弱 | ffmpeg 版本变化会导致正则失配 | 加 `-hide_banner` + 版本兜底；建议改用 `-of json` 不可行（检测类滤镜只输出 stderr），保持正则但在 CI 固定 ffmpeg 版本 |
| 片头片尾 `-make_card` | 思路对 | concat 参数一致性风险高 | 见 §1.6 坑 |

## 2. 清晰度增强方案裁决（4GB 显存现实）

### 2.1 三方案对比

| 方案 | 运行需求 | 4GB 显存可行性 | 数字人场景实际效果 | 裁决 |
|---|---|---|---|---|
| **ffmpeg 滤镜链**（lanczos+unsharp+hqdn3d） | 纯 CPU，任何机器 | **完全可行** | 提升对比/锐度/去噪，无法"无中生有"细节 | **采用** |
| **Real-ESRGAN ncnn-vulkan** | Vulkan GPU 或 CPU | **可行**（ncnn-vulkan 版不依赖 CUDA/Torch，可用核显或 CPU，显存需求低） | 对压缩块状伪影有明显修复；但**速度极慢**（1080p 视频逐帧超分，CPU 上约 1~5 fps，60 秒视频需 12 分钟~1 小时） | 备选，不建议默认开 |
| **GFPGAN / CodeFormer** | PyTorch + CUDA | **不可行/极度勉强**。二者均需加载 face detection（RetinaFace）+ 生成模型，4GB 显存下 512 输出分辨率基本 OOM 或需降到 256 且极慢 | 仅修复人脸区域，对**口型边缘、牙齿、发丝**有改善；但会引入时序闪烁（逐帧独立推理，帧间不连贯） | **不采用** |

### 2.2 关键裁决理由

1. **收益与成本严重不匹配**：你的数字人走**云 API** 路线，云端输出的口播视频本身就是干净的高分辨率渲染（无网络压缩伪影）。超分工具的价值主要在"修复低质老片/严重压缩源"，对干净源收益趋近于零，而锐化后的 `unsharp` 反而更可控。
2. **时序闪烁是致命伤**：Real-ESRGAN / GFPGAN / CodeFormer 都是**逐帧独立**推理，没有时序一致性约束。对静态图像效果好，但用在视频上会产生**帧间抖动**（脸部纹理一闪一闪），比"略微不够锐"更伤观感。Real-ESRGAN 官方模型亦无视频时序模块。
3. **帧化管线的工程代价**：你现有 `enhance.py` 的 `_enhance_realesrgan` 已走"抽帧→超分→concat 回封"路线，这条路线会有：磁盘 IO 爆炸（1800 张 PNG ≈ 数 GB）、PNG 无损体积巨大、concat 时间基错位风险。
4. **4GB 显存的红线**：4GB 若跑 GFPGAN/CodeFormer，需 `--tile` 分块 + 降到 256 分辨率，此时修复效果已不如直接 ffmpeg 锐化，且仍可能 OOM。

### 2.3 落地建议

```python
# config.yaml 建议
enhance:
  enabled: true
  engine: ffmpeg          # 不用 realesrgan
  denoise: true
  denoise_strength: 1.5:1.2:4:4
  sharpen: true
  sharpen_amount: 0.55     # 上限 0.8
  contrast: 1.03
  saturation: 1.06
  target_crf: 20
  realesrgan_bin: ""
```

**若后续确实需要锐化加强**：优先调 `unsharp` 的第 3 位（luma amount）到 0.7，并叠一个轻微 `cas`（Contrast Adaptive Sharpen）：

```bash
-vf "scale=1080:1920:flags=lanczos,unsharp=5:5:0.60:5:5:0.0,cas=strength=0.35"
```

`cas` 是边缘自适应锐化，比 unsharp 更不易产生光晕，且**是纯 ffmpeg 内置滤镜，零额外依赖**。这是本项调研给出的最优解。

## 3. 字幕工程

### 3.1 抖音口播字幕样式规范（建议）

| 项目 | 建议值 | 依据 |
|---|---|---|
| 每行字数 | **12~16 字**（你 config 用 16，可接受；建议 14） | 1080 宽下 14 字可用 56px 字号 + 8% 安全边距 |
| 最多行数 | **2 行** | 3 行以上遮挡画面且阅读负担大 |
| 位置 | 底部基线距底边 **320px**（你 config 值正确） | 需避开抖音 UI 的进度条、文案区、右侧互动栏 |
| 右侧安全边距 | **≥ 100px** | 抖音右侧有心/评/转竖排按钮 |
| 顶部安全边距 | **≥ 180px** | 顶部有账号信息与顶部导航 |
| 字号 | 56px @1080×1920 | 手机全屏观看清晰 |
| 字体 | 无衬线粗体（思源黑体 Bold / 阿里巴巴普惠体 Bold） | 抖音生态通用；**必须确认字体商用授权** |
| 描边 | 3~4px 深色（黑或深灰）+ 轻微阴影 | 保证任何背景可读 |
| 底框 | 若用底框，黑底 opacity 150/255（≈59%） | 你 config 值合理 |
| 单条停留 | **与语音时长一致**，最短 ≥0.8s | 低于 0.8s 视觉上闪，读不完 |
| 重点词高亮 | 变色（如 #FFD400）+ 可轻微放大 | 你现有 `subtitle.py` 已实现，方向对 |
| 标点 | 句末标点可省略，句中逗号保留或改为空格 | 短视频字幕惯例 |

**关键：字幕不能压到抖音的 UI 安全区。** 建议在渲染时画一条 `safe_area` 辅助参考线（仅开发期可见），确认 320px 底部边距在你的画面构图下不遮挡人物下巴/手部。

### 3.2 从 TTS 直出词级时间戳（路 A）

**你现有的做法（从 TTS 直接拿时间轴）在云 TTS 下是否成立？答案是"部分成立，不能作为唯一路径"。**

| TTS 服务 | 是否提供词/字级时间戳 | 置信度 | 说明 |
|---|---|---|---|
| Azure Speech (Cognitive Services) | **是** | 高 | 提供 `WordBoundary` 事件（含 `offset`/`duration`，单位 100ns tick），业界最成熟。SSML 驱动，支持中文。**注意 `WordBoundary` 对中文是按"词"切分，不是单字，需按 `text` 字段回填** |
| 微软 Edge TTS (`edge-tts`) | **是（部分）** | 中 | `edge-tts` Python 库提供 `SubMaker`，从音频流的 metadata 中解析 `WordBoundary`。**但你 config 里 `zh-CN-XiaoxiaoNeural` 就是 edge-tts 的 voice 名**，说明你现在走的是这条路，且已在用时间戳——这条链在"不换云 TTS"的前提下成立 |
| 火山引擎（豆包）语音合成 | **是** | 中 | 提供带时间戳的合成接口（需在请求中开启）。`[待核验]` 具体参数名与返回结构需查火山官方文档 |
| 阿里云智能语音交互（CosyVoice / Sambert） | **是** | 中 | 部分接口支持字级时间戳输出，需确认具体版本 |
| OpenAI TTS / ElevenLabs | **否（不返回时间戳）** | 中 | 需 ASR 回退 |

**结论**：从 TTS 直出时间戳是**最优路径（零额外成本、时间戳精确到毫秒、无需对齐）**，但**强绑定到具体 TTS 厂商**。架构上必须做抽象：

```python
class TimestampProvider(Protocol):
    def get_word_timestamps(self, text: str, audio_path: str) -> list[dict]:
        """返回 [{'word': '人工智能', 'start': 0.12, 'end': 0.68}, ...]"""
```

- 若 TTS provider 声明 `supports_timestamps = True` → 走直出
- 否则 → 自动降级到 ASR（§3.3）

### 3.3 ASR 回退（路 B）

| 方案 | 4GB 本地可行性 | 价格 | 精度 | 建议 |
|---|---|---|---|---|
| **faster-whisper (large-v3 int8 / medium)** | **可行**。int8 量化后 medium 约 2GB 显存，large-v3 int8 约 3GB | 开源免费 | 中文优秀，`word_timestamps=True` 提供词级 | **本地回退首选** |
| Whisper (openai 原版) | 勉强，显存占用高于 faster-whisper | 免费 | 同上 | 次于 faster-whisper |
| **FunASR (Paraformer)** | **可行**，CPU 亦可（约 1~2GB 显存） | 开源免费 | **中文最强**，原生输出**字级时间戳**，阿里达摩院出品 | **中文场景最佳**，强烈推荐 |
| 火山引擎 ASR | 不适用（云） | 按量计费 `[待核验]` 具体单价 | 高 | 云端备选 |
| 阿里云 ASR | 不适用 | 按量计费 `[待核验]` | 高 | 云端备选 |

**裁决**：

1. **本地回退首选 FunASR（Paraformer）** —— 它是中文 ASR 里字级时间戳最扎实的，且对 4GB 显存友好（甚至 CPU 可跑）。对口播字幕的"逐字对齐"体验最好。
2. **备选 faster-whisper** —— 多语言场景更通用，中文略逊于 Paraformer，但生态成熟、部署简单。
3. **云端 ASR 价格未核验** —— 本任务未取得火山/阿里 ASR 的当前计价，标 `[待核验]`。鉴于本地 FunASR 免费且效果足够，**不建议为此付费**。

**关键工程坑**：ASR 回退出的词级时间戳与原始口播稿**可能有错字**（同音字）。必须做**文本对齐校正**：用 ASR 时间戳作为"时间锚点"，用原始口播稿作为"正确文本"，通过编辑距离对齐（如 `difflib.SequenceMatcher` 或 `jiwer`）把正确文本套到 ASR 的时间轴上。否则字幕会出现错别字。

### 4.2 自动化方案（抽帧 + 合成）

三步法，全部可用你现有技术栈实现：

```bash
# Step 1: 抽帧候选（取视频 10%~35% 区间的清晰帧，避开开场黑帧与片尾）
ffmpeg -y -hide_banner -ss 3.0 -i final.mp4 -frames:v 1 -q:v 2 \
  -vf "scale=1080:1920:flags=lanczos,format=yuv420p" cover_raw.jpg
```

```bash
# Step 2: 自动挑选最清晰的一帧作为封面底图（用 ffmpeg 的 blurdetect/信号统计辅助）
ffmpeg -hide_banner -ss 0 -t 10 -i final.mp4 \
  -vf "select='gt(scene,0.3)',metadata=print:file=-" -f null - 2>&1 | head -40
```

```python
# Step 3: PIL 合成标题（复用你现有 postprocess.py 的 _make_card 思路）
from PIL import Image, ImageDraw, ImageFont, ImageFilter

W, H = 1080, 1920
base = Image.open("cover_raw.jpg").convert("RGB")

# 顶部/底部加渐变遮罩，提升文字对比度
overlay = Image.new("RGBA", (W, H), (0, 0, 0, 0))
od = ImageDraw.Draw(overlay)
for y in range(int(H * 0.55), H):                       # 底部渐黑
    alpha = int(190 * (y - H * 0.55) / (H * 0.45))
    od.line([(0, y), (W, y)], fill=(0, 0, 0, alpha))
base = Image.alpha_composite(base.convert("RGBA"), overlay).convert("RGB")

draw = ImageDraw.Draw(base)
font = ImageFont.truetype("assets/fonts/SourceHanSansSC-Bold.otf", 86)

title = "3分钟搞懂大模型"          # ≤ 12 字
# 手写换行（中文无空格，不能靠 textwrap）
lines = [title[i:i + 9] for i in range(0, len(title), 9)][:2]
y = int(H * 0.72)
for line in lines:
    w = draw.textlength(line, font=font)
    x = (W - w) / 2
    draw.text((x, y), line, font=font, fill=(255, 255, 255),
              stroke_width=6, stroke_fill=(0, 0, 0))     # 描边保证可读
    y += 110

base.save("cover.jpg", quality=92, optimize=True)
```

**自动化增强建议：**

1. **封面选帧策略**：可以先生成**没有字幕的第 0.x 秒帧**作为底图（避免字幕重复），或直接让封面底图取"数字人正面、口型闭合"的瞬间。可对你的数字人视频做一个简单检测：抽取 5 个候选帧，用 `cv2.Laplacian` 方差选最清晰的一帧。
2. **封面标题与视频标题分离**：`publish/drafts.py` 的发布包里应包含 `cover.jpg` 与 `title.txt` 两个独立字段，避免把长标题硬塞进封面。
3. **A/B 封面**：抖音支持发布后修改封面。可在 `publisher.py` 状态机加一个 `cover_swap` 后置任务（人工触发），但**平台侧无 API 支持**，属人工操作。

### 5.3 端点结论

1. **config 中的 `upload_url: https://open.douyin.com/video/upload/video/` 是错的** —— 实测 404。正确候选为 `/video/upload/`（旧）或 `/api/douyin/v1/video/upload_video/`（新）。**必须修改。**
2. **config 中的 `create_url: https://open.douyin.com/video/create/` 路径存在**，但属于旧版路由；现代路由为 `/api/douyin/v1/video/create_video/`。二者实测均存在，但**存在 ≠ 有权调用**（见 §6）。
3. **两套错误码体系并存**：
   - `open.douyin.com` 根路径族返回 `{"data":{...},"extra":{...}}`，错误码 `2190002`（无效）/`2190008`（过期）
   - `/api/douyin/v1/...` 族返回 `{"err_no":28001003,"err_msg":"..."}`
   - **你的 `douyin.py` 只解析了 `data.error_code`，对 `/api/douyin/v1/` 的 `err_no` 完全不识别**，会导致现代路由下所有错误被吞成"成功"。**这是必须修的真实 bug**（见 §8.4）。
4. **`/oauth/client_token/` 存在**，是获取 `client_token` 的正规入口（`client_token` 是应用级凭证，用于无需用户授权的接口）。
5. **`/api/douyin/v1/video/video_basic_info/`** 经文档站内搜索确认存在（见 §5.4），且文档给出的请求头名为 **`access-token`（带连字符）**，示例值形如 `act.943da17996fb...`。

### 6.2 「代发」的规范限制 `[文档实测]`

实读来源：`.../operation-standard/platform-capabilities/usage-spec`（页面标注 **更新时间 2025-06-06 15:44:18**）。这是**本次调研对你项目最关键的单条发现**：

> **原文**：「开发者在使用**代替用户发布内容到抖音**的相关能力时，仅可用于**企业内部或者签约的账号**的内容管理。同时，**实时发布或者预设发布需要用户自己在第三方应用上进行操作**，且需明确告知用户将把当前内容（包括素材内容、标题、话题及其他信息等）同步到哪个抖音上或在哪个抖音上同步删除，并**支持用户勾选「是否同步」、「是否删除」**。」

**解读**：

1. 「代替用户发布」**仅限于企业内部账号或签约账号**。你运营的是自己公司的矩阵账号 → 这一条**理论上可以满足**（内部账号）。
2. 但「**预设发布需要用户自己在第三方应用上进行操作**」——即：**定时发布这件事，平台要求最后一步由人触发**。你的 `scheduler.py` APScheduler 全自动定时发布，**不符合该规范**。
3. 必须支持「是否同步」勾选框 —— 意味着产品上必须有"人工确认"环节。

> **同时注意到**：该规范中「**不得大量发布同质化内容，包括但不限于：同个账号多次发布相似视频、相似视频发布到多个账号上**」——这对"AI 批量生成 + 矩阵分发"的商业模式是**直接的合规打击**。你的 `quality/checker.py` 有 `max_similarity: 0.72` 的去重阈值，这一步在合规上是**必需的而非可选的**，且 0.72 可能不够严格。

### 7.4 推荐的合法退路（明确结论）

**推荐：本地发布就绪包 + 人工确认（你现有 `drafts.py` 方向完全正确）。**

具体形态：

1. **Pipeline 出口产出"发布就绪包"**：`video.mp4` + `cover.jpg` + `title.txt` + `desc.txt` + `tags.txt` + `ai_label.txt` + `manifest.json`（含 hash、时长、码率、AI 标识字段）。

## 8. 发布 Adapter 接口设计建议

### 8.1 分层（保留你现有架构，仅补充）

```
Content Pipeline → Video Pipeline → Publish Adapter ─┬─ LocalDraftAdapter  (推荐主力)
                                                     ├─ DouyinSdkAdapter  (拿到资质后，人工确认)
                                                     └─ DryRunAdapter     (测试/CI)
```

**关键设计原则**：Adapter 层必须能**诚实表达"我做不到全自动"**。不要为了接口好看而假装存在一条投递 API。

### 8.2 接口定义建议

```python
from __future__ import annotations
from dataclasses import dataclass, field
from enum import Enum
from typing import Any, Optional, Protocol


class PublishMode(str, Enum):
    LOCAL_DRAFT = "local_draft"      # 本地就绪包 + 人工发布（默认、推荐）
    DOUYIN_SDK = "douyin_sdk"        # 官方 SDK/H5 投稿（需资质，人工确认）
    DRY_RUN = "dry_run"


class PublishState(str, Enum):
    PENDING = "pending"
    READY = "ready"                  # 就绪包已生成
    AWAITING_HUMAN = "awaiting_human"  # 等待人工确认（合规必需环节）
    SUBMITTED = "submitted"          # 已提交（抖音侧审核中）
    PUBLISHED = "published"
    FAILED = "failed"
    BLOCKED = "blocked"              # 因合规/资质被阻断，需人工介入


@dataclass
class PublishPackage:
    video_path: str
    cover_path: str
    title: str
    description: str
    tags: list[str]
    ai_generated: bool = True        # 强制显式声明，默认 True
    ai_label_text: str = "本内容由 AI 生成"
    schedule_at: Optional[str] = None  # ISO8601，仅作提示，不作为自动投递依据
    idempotency_key: str = ""        # 幂等键：sha256(video)+title+date
    manifest: dict[str, Any] = field(default_factory=dict)


@dataclass
class PublishResult:
    success: bool
    state: PublishState
    message: str = ""
    item_id: str = ""
    url: str = ""
    raw: dict[str, Any] = field(default_factory=dict)


class PublishAdapter(Protocol):
    name: str

    def capabilities(self) -> dict[str, Any]:
        """返回能力声明，供上层决策。
        例：{'auto_publish': False, 'scheduled': False,
             'requires_human_confirm': True, 'requires_user_auth': True}"""

    def prepare(self, pkg: PublishPackage) -> PublishResult:
        """生成发布就绪包/发起投稿。不做任何无授权的投递尝试。"""

    def confirm(self, item_id: str) -> PublishResult:
        """人工确认后回写（合规必需）。"""

    def status(self, item_id: str) -> PublishResult:
        """查询状态。若上游无查询能力，必须显式返回 state=BLOCKED 并说明原因，
        而不是返回 success=True 假装成功。"""
```

### 8.3 队列 / 重试 / 幂等 / 状态回写 / 告警

| 机制 | 建议实现 | 理由 |
|---|---|---|
| **队列** | SQLite 表 `publish_jobs(id, idempotency_key UNIQUE, state, payload, attempts, last_error, created_at, updated_at)` | 你已有 `db.py` + SQLite，直接扩展即可，无需引入 Redis |
| **幂等** | `idempotency_key = sha256(video_bytes)[:16] + ":" + title_hash`，DB 唯一索引 | 防止重试导致重复发布。**这是最重要的机制** |
| **重试** | 指数退避 `delay = base * 2**attempts`，base=2s，max_retry=3，**仅对可重试错误重试** | 你现有 `max_retry: 3, retry_backoff: 2.0` 正确 |
| **不可重试错误** | 4xx 类（参数错误、权限不足、资质缺失、内容违规）**立即置 FAILED 并告警**，不重试 | 重试无意义且可能触发风控 |
| **状态回写** | 每次状态变更写 `publish_jobs` + 追加 `publish_events` 审计表 | 可追溯，合规排查需要 |
| **失败告警** | `webhook_url` 推送 + 本地日志 ERROR；连续 N 次失败触发熔断（暂停队列） | 你已有 `webhook_url` 字段，接上即可 |
| **人工确认门** | `state=AWAITING_HUMAN` 时**暂停队列**，等待 `confirm()` | 合规必需（§6.2） |
| **定时发布** | **明确降级为"提醒"而非"投递"**：`scheduler.py` 到点后生成就绪包 + 推送通知，**由人发布** | 官方规范要求预设发布由人操作 |

### 8.4 你现有 `douyin.py` 必须修的真实 bug

| Bug | 位置 | 问题 | 修法 |
|---|---|---|---|
| **错误码体系不识别** | `upload_video` / `create_video` 只读 `data.get("error_code")` | `/api/douyin/v1/...` 族返回 `{"err_no":28001003,"err_msg":...}`，代码读不到 → `error_code` 为 `None` → 判定为"成功" → **静默失败** | 统一解析函数，兼容 `error_code` / `err_no` / `err_msg` / `description` 三种形态 |

### 9.2 肖像权 / 声音权 / 人格权风险清单

| 风险项 | 全 AI 虚拟人是否绕开？ | 说明 | 风险等级 |
|---|---|---|---|
| **肖像权** | **基本绕开，但有边界** | 若虚拟人形象为纯 AI 生成、不源自任何真人照片，则不构成对特定自然人的肖像权侵害。**但**：若生成结果与某真实公众人物"可识别地相似"（尤其面部特征、标志性造型），仍可能被主张侵权 | 中 |
| **AI 生成形象的知识产权归属** | **需明确** | 虚拟人形象的著作权归属与可保护性存在争议。建议：(1) 保存完整的生成参数、seed、prompt、模型版本作为创作过程证据；(2) 在服务商协议中明确形象资产归你所有（**云 API 服务商的条款必须逐条读**，很多服务商保留对生成内容的使用权）；(3) 考虑对固定形象做商标注册 | 中高 |
| **声音权** | **有条件绕开** | TTS 合成音色若为服务商提供的通用音色（如你 config 的 `zh-CN-XiaoxiaoNeural`），一般由服务商承担音色合规责任。**但**若使用"声音克隆"功能还原真人音色，则直接触及声音权，需取得授权 | 中（用通用音色）/ 高（用克隆音色） |
| **与未成年人相似度** | **不要触碰** | 虚拟人应设计为**明确成年**的外观。避免"幼态""学生装"等特征。不仅涉法，也是平台重点管控方向 | 高（应主动规避） |
