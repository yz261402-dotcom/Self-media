## 0. 一句话结论

**技术上全部可落地，成本可控；但「全自动无人值守发布到抖音」在官方路径下不成立——这是本次调研最重要的发现，且会改变项目的产品定义。**

必须把项目从「无人值守内容工厂」重新定义为 **「AI 内容生产 + 发布就绪包 + 人工确认发布」的人机协同产线**。其余环节（形象一致性、口播驱动、TTS、质检、后处理、字幕）全部有明确选型，无需换硬件。

## 2. 冲突裁决（本次收口的核心工作）

### 2.1 【重大冲突】抖音到底能不能 API 全自动发布？—— 裁决：**V1 不能（对个人开发者）**

两份文件给了**表面相反**的结论，必须裁清：

| | 01 号文件 | 05 号文件 |
|---|---|---|
| 主张 | 存在官方接口 `POST /api/douyin/v1/video/create_video/`，Scope `video.create.bind`，75 条/天上限 | **移动/网站应用 OpenAPI 全量清单里没有任何"上传视频并直接发布为作品"的服务端接口**；能力形态是「拉起抖音 App → 内容填入编辑页 → **用户手动点发布**」 |
| 证据 | `create-video` 接口文档页（Jina Reader 渲染）+ 官方错误码表 | `openapi/list` 全量清单实读 + 能力准入页 `platform-capabilities/useclue`（页面更新 2026-07-14）+ 使用规范 `usage-spec`（更新 2025-06-06） |
| 置信度 | 高（实测） | 高（实测） |

**裁决结论：两份都对，但描述的是两个不同层面，合起来才完整。**

1. **接口路径确实存在** —— 05 自己用 curl 实测证明了这点：`POST https://open.douyin.com/api/douyin/v1/video/create_video/` 返回 `200 {"error_code":2190002,"description":"access_token无效"}`。按 `open.douyin.com` 的网关判别规则（存在→200+业务错误码，不存在→404 `Unsupported path(Janus)`），**该端点真实存在**。01 的发现成立。
2. **但「路径存在 ≠ 有权调用 ≠ 全自动」** —— 05 找到了更关键的一层，这层 01 没覆盖：
   - **资质墙**：能力准入页原文「**不再向个体工商户类型主体开放**；若主体类型为企业，需满足**注册资本≥50万且注册时间≥1年**」；应用类型「**仅对创作工具、社区、硬件配套、游戏类开放**」；使用场景「如涉及企业宣传、商品介绍、**诱导分享等营销类内容**，**不开放该能力准入**」。→ **个人开发者直接无资格。**
   - **形态墙**：能力形态是「从 App 拉起抖音 App，投稿内容直接传入内容编辑页/发布页」「用户可手动添加/修改参数，**手动操作发布**」。
   - **规范墙**（最致命，05 §6.2 引 `usage-spec` 原文）：「开发者在使用代替用户发布内容到抖音的相关能力时，**仅可用于企业内部或者签约的账号的内容管理**。同时，**实时发布或者预设发布需要用户自己在第三方应用上进行操作**」，且须支持用户勾选「是否同步」「是否删除」。→ **定时自动发布这件事本身，规范要求最后一步由人触发。**

**对本项目的最终口径**：

> **V1 放弃「无人值守全自动发布」这一需求。** 原需求书第十三节验收标准里「加入发布队列 → 按照计划时间发布 → 记录发布结果」这条链，**在个人开发者身份下无法以官方方式实现**。这不是工程难度问题，是资质与规范问题，砸钱写代码解决不了。
>
> 改为：**管线产出「发布就绪包」 → 人工在抖音 App 内确认发布 → 系统回写发布结果**。你现有的 `drafts.py` 方向**完全正确**，应作为 V1 主力而非临时退路。

**必须写入立项文档的产品定义修正**：本项目是「**AI 内容生产系统 + 发布辅助**」，不是「AI 自动发布系统」。

### 2.2 【次级冲突】每日发布条数上限 75 条 —— 裁决：**01 号胜**

01 引官方错误码表 `2114007`「一个用户在一个应用下，一天最多发布 75 个作品」；05 §6.3 标记为「未核验」。

→ **采信 01**（错误码表是一手文档，证据更强）。但**对你的排产无实际影响**：按 1~3 条/天排产，与 75 条上限有两个数量级余量，不构成工程约束。

### 2.3 【内部矛盾】02 号文件自身对「三段解耦」怎么实现前后不一致 —— 裁决：**采 A5，A9 降为条件分支**

02 的 A5 说「**不要**三段分别生成再拼（拼接会引入颈部接缝、发丝边缘、光照不一致三类瑕疵）」，但 A9 又说「**首选分层生成**（背景独立生成 → 人物云 API 生成 → 抠图合成）」——A9 的「抠图合成」正是 A5 反对的拼接。

**裁决**：
- **默认走 A5**（参考图数组 + 提示词模板，**一次调用生成完整画面**）——理由：云模型已原生支持多图参考 + 角色一致性，一次生成天然规避接缝/光照问题。
- **A9 降级为按需分支**：仅当出现「必须严格锁定人物像素位置」的需求（例如要做固定机位的系列栏目）才启用分层合成。
- **落地取舍**：先用 A5 跑通；把 A9 记入待办而非 V1 实现范围。

### 2.4 【重大风险，两份文件都没连起来看】推荐的身份门禁方案踩了许可证雷

- 02 的 **A7 推荐用 ArcFace embedding 做身份一致性门禁**（方案核心）；
- 02 的 **A8 同时实测到**：insightface 官方 README 原文「available for **non-commercial research purposes only**」，且该许可**连带** InstantID / PuLID / PhotoMaker / IP-Adapter-FaceID。

**这两条合起来意味着：02 推荐的质检门禁，其依赖模型禁止商用。** 而本项目是商业项目。

**裁决与处置（不能自行拍板，列为法务待确认）**：
- 这是**待确认的法律灰区**，不是可以工程绕过的技术问题。「内部质检」是否构成「商用」取决于许可解释与当地司法，**我不替你做法律判断**。
- **三条并行处置**：(a) 立刻排查是否有许可宽松的人脸识别/相似度模型可替代（Apache-2.0/MIT 系）；(b) 若必须用 insightface 系，读完整 LICENSE 原文 + 询问上游；(c) 设计上把门禁做成**可插拔**，替换实现不改业务层。
- **旁证降低风险**：02 A8 自己也注明「生成结果的商用性取决于**云服务条款**，不取决于本地质检脚本」——即风险集中在**本地质检环节**，与成片本身的商业可用性无关。这是个可控范围，但必须在 PRD 里显式登记。

### 2.5 【补充】03 提示的两条工程约束，别漏

- **火山并发=1** → 日更多条必须做**串行队列**，不是并发。这会直接影响 `pipeline` 的调度设计（不能用并发假设）。
- **火山/阿里要求图片与音频是公网可访问 URL** → 需要**对象存储**（并配 TTL + 用后即删，见 03 R10）。当前 demo 是纯本地路径假设，这条是新增的基础设施依赖。

## 6. 立项级建议：三条形态决策（建议写死进 PRD）

1. **V1 不做直播、不做无人直播。** 01 P4 实测确认：平台「虚拟人须真人驱动」的约束**只针对直播**；短视频口播走 AI 标识路径。**这是产品形态上的实质性合规优势，是免费拿到的护栏，不要自己去碰红线。**
2. **主动标识「这是一位 AI 主播」，并把它做成栏目人设。** 在 AI 科普赛道，「AI 讲 AI」本身自洽，主动标识的人设成本远低于其他赛道；而被动被平台检测出未标识 = 风险路径。**主动标识 ≈ 合规 + 记忆点，是双赢而非妥协。**
3. **内容定位「AI 工具实操 + 认知科普」，单条 1 个知识点，60~75 秒起。** 时长做**可 A/B 参数**而非写死；首期用「B 工具实操 + C 认知科普」为主体，用系列化外壳包装（01 §1.2）。

## 附：本次调研的方法学沉淀（可复用）

- **抖音文档站是 SPA，`curl` 拿不到正文** → `curl https://r.jina.ai/<doc-url>` 可渲染出正文；`sitemap/home/index*.xml` 可枚举全部 **7,470 条**文档路径。
- **`open.douyin.com` 网关判别法**：存在→`200`+业务错误码；不存在→`404`+`Unsupported path(Janus)`。**据此可无凭证判定端点真实存在性**（本次 26 条端点的判定全靠这个）。
- **踩坑警示**：URL `.../dop/ability/content-management/video.create.bind` 渲染出来的是「分享至抖音私信/群」页，**不是**发布接口。真正的发布接口在 `develop/openapi/video-management/douyin/create-video/` 下。（01 §6.4 已记录）
- **两套错误码体系并存**：`open.douyin.com` 根路径族返回 `{"data":{"error_code":...}}`；`/api/douyin/v1/...` 族返回 `{"err_no":...}`。这是 F3 那个 bug 的根源。
- **GitHub 元数据**：未认证 API 限流 60/hr（共享出口 IP 极易耗尽）→ 用已认证 `gh api`（5000/hr）。
- **本机路径坑**：git-bash 下 PATH 无 python/pip（需 Anaconda 绝对路径 `D:\anaconda3`）；Windows 原生 curl/jq 不认 MSYS `/tmp`、`/c/...` 路径（需 `C:/tmp/` 原生路径）。
